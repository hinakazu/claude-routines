**cronとPATH管理**
• cronジョブでは `.bashrc`/`.zshrc` が読み込まれず、PATH が `/usr/bin:/bin` 程度に制限されるため `claude` や `node` 等のコマンドが exit 127 で無音終了する。スクリプト先頭で `PATH=/usr/local/bin:/usr/bin:/bin:$HOME/.local/bin` のように明示指定するか、コマンドを絶対パスで記述するのが最も確実な対策。
• crontabファイル冒頭に `PATH=...` を一行追加すると、そのcrontab内の全ジョブに適用できる（個別スクリプトへの対応不要）。
• デバッグ時は一時的に `env > /tmp/cron-env.txt` をcronで実行し、インタラクティブシェルの `env` と比較するのが最速の原因特定法。`#!/bin/bash` シェバンと実行権限（`chmod +x`）も必ず確認する。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` には多くの例外がある：`if` 条件式・`!` 否定・`||` の左辺はexit しない。`((count--))` が 0 を返すと exit 1 扱いでスクリプトが終了する罠があり、`|| true` を付けて回避する。
• `local var=$(cmd)` は `cmd` の終了ステータスを隠すため `set -e` が発火しない。`local var` と `var=$(cmd)` を別行に書くことで正しく検知できる。
• 推奨パターンは `set -euo pipefail` + `trap 'echo "ERROR: line $LINENO exit $?" >&2' ERR` + `trap cleanup EXIT` の三点セット。ERR trapはデフォルトではサブシェルに継承されないため、関数内でも有効にするには `set -E`（errtrace）が必要。

**git non-fast-forward pushとrebaseの操作順序**
• 自動化スクリプトでは git 操作前に `git status --porcelain` でdirty treeをチェックし、未コミット変更があれば中断する。変更のある状態で `git pull --rebase` を実行すると rebase がブロックされ、操作失敗の原因になる。
• 安全な操作順序は「`pull --rebase` → 変更 → `add` → `commit` → `push`」。変更後に pull するとコンフリクトリスクが高まる。`rebase.autostash = true` を git config に設定すると、dirty tree でも pull --rebase が自動でstash→rebase→unstashするため自動化スクリプトで重宝する。
• rebase後のpushでnon-fast-forwardエラーが出る場合は `git push --force-with-lease` を使う。`--force` と違い、リモートに自分が知らないコミットがあれば失敗させてくれる安全なforce push。

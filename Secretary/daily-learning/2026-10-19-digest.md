**cronとPATH管理**
• cronは起動時にPATH=/usr/bin:/binの最小環境しか持たず、.zshrcや.bashrcは一切読み込まれない。/usr/local/binや独自インストール先のコマンドは必ずexit 127で無音失敗する
• 対策は3つ：①crontabファイルの先頭にPATH=行を追加（そのcrontab全体に適用）②各スクリプト冒頭でexport PATHを明示③コマンドをすべてフルパスで記述
• macOSではcronはSequoia以降で動作しないケースが報告されており、Appleはlaunchdへの移行を推奨。launchdではplistのEnvironmentVariablesキーでPATHを設定できる
• cronでもlaunchdでも出力を>> /var/log/xxx.log 2>&1でリダイレクトしないと無音失敗を追えない

**`set -e` のサイレント終了とエラーハンドリング設計**
• set -eだけでなく`set -Eeuo pipefail`をセットで使うのが2026年時点のベストプラクティス。-uは未定義変数タイポを検出、-o pipefailはパイプライン途中の失敗を検出、-Eはfunctions内でもERR trapが正しく発火する
• `trap 'echo "ERROR at line $LINENO: $BASH_COMMAND" >&2' ERR` と `trap 'cleanup' EXIT` を組み合わせると、失敗した行番号とコマンドが即座にログに出る
• set -eが効かない落とし穴：①`$(...)` コマンド置換内の失敗②`((count--))` が0を返したとき③`&&`の左辺の失敗。これらには明示的なエラーハンドリングが必要
• set -xをデバッグ時に加えると実行コマンドと展開後の引数が全部ログに出る

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトでの正しい順序は「pull → 変更 → commit → push」。変更後にpullするとunstaged changesがrebaseをブロックして失敗する
• `git pull --rebase --autostash` を使うと未コミット変更があるdirty repoでもstash→rebase→unstashを自動で行い、non-fast-forwardエラーを防げる
• git configに`pull.rebase=true`と`rebase.autoStash=true`を設定しておくと`git pull`だけで同じ効果が得られる
• force pushが必要なときは`--force`ではなく`--force-with-lease`を使う。リモートに自分が取得していない変更があれば拒否してくれる

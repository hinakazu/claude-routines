**cronとPATH管理**
• cronジョブはユーザーのシェル設定（.zshrc/.bashrc）を読み込まず、`PATH=/usr/bin:/bin` のみという最小限の環境で動作する。「手動では動くのにcronで動かない」の原因はほぼこれ。
• 解決策は3層構造で考える: ①crontabファイル冒頭に `SHELL=/bin/bash` と `PATH=/usr/local/bin:/usr/bin:/bin` を明示宣言、②スクリプト内は必ず絶対パスを使う（/usr/local/bin/node等）、③ラッパースクリプト経由で環境変数をセットアップしてから本体を呼ぶ。
• macOSではcronより launchd が推奨: `~/Library/LaunchAgents/` に置くplistファイルの `EnvironmentVariables` キーでPATHを直接指定でき、「works manually, fails in launchd」問題を根本回避できる。スリープ/ウェイク後の実行補償もlaunchdが管理する。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は条件文・`||`/`&&` チェーン・サブシェル内のコマンド失敗を無視するため「ログなしで静かに死ぬ」問題が起きる。`set -euo pipefail`（`-u`=未初期化変数検出、`-o pipefail`=パイプ途中の失敗検出）がより安全なセット。
• 推奨パターン: スクリプト先頭に `set -euo pipefail` を宣言し、`trap cleanup EXIT` で終了時クリーンアップを必ず実行する。EXITトラップはエラー終了・正常終了どちらでも動作するため、一元化に適している。
• ERRトラップは失敗コマンドの終了コードとコマンド名をログに残す専用処理として使い、クリーンアップはEXITトラップで行う二段構えが本番スクリプトの標準設計。

**git non-fast-forward push と自動化スクリプトの操作順序**
• non-fast-forwardエラーの本質: ローカルブランチとリモートが分岐し、ローカルの先端コミットがリモートの先端の直接祖先でなくなった状態。複数箇所（cronとローカルPC等）から同一リポジトリへpushするほど発生頻度が上がる。
• 自動化スクリプトでの安全な操作順序: `git stash`（未コミット変更あれば）→ `git pull --rebase` → ファイル作業 → `git add` → `git commit` → `git push`。pull前にunstagedな変更があるとrebaseがブロックされるため、作業前にstashかcommitが必須。
• 追加のベストプラクティス: `git status` でuntracked/modified fileを確認してからpullする; Conventional Commits形式のコミットメッセージをCIで強制するとログから自動化起因のコミットを識別しやすい。

**cronとPATH管理**
• cronはユーザーの `.zshrc` / `.bashrc` を読み込まないため、スクリプト冒頭で `export PATH=/usr/local/bin:/usr/bin:/bin:/custom/path` を明示的に設定することが必須。絶対パスで全コマンドを記述するのも有効な代替策。
• デバッグは `env > /tmp/cron_env.txt` を仕込んだジョブを走らせ、インタラクティブ環境のPATHと比較するのが最速。
• `crontab` の先頭行に `PATH=...` を書く方法もあるが、各スクリプト内で自己完結させる方がポータブル。テンプレートは `#!/bin/bash\nset -euo pipefail\nexport PATH=/usr/local/bin:/usr/bin:/bin\ncd /absolute/path || exit 1`

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は条件式（`if`/`&&`/`||`）の中では発動せず、コマンド置換（`$(...)` 内）にも継承されないため、「安全に見えてデバッグを難しくする諸刃の剣」。
• 最強の組み合わせは `set -euo pipefail` ＋ `trap 'echo "Error on line $LINENO: $BASH_COMMAND" >&2' ERR`。これで失敗行番号とコマンド名がログに残る。
• `((count--))` が `count=0` のとき非ゼロ終了して `set -e` がスクリプトを強制終了するバグに注意。`((count--)) || true` で回避。ソースライブラリファイルでは `set -e` を使わない（呼び出し元のシェル挙動を変えるリスクあり）。

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトでの正しい操作順序は `git fetch origin` → `git rebase origin/<branch>` → `git push`。コミット後にpullすると unstaged changes が残り rebase がブロックされる。
• `git pull` 戦略はスクリプト内でフラグを明示（`--rebase` or `--ff-only`）し、ランナー設定に依存しない。`--ff-only` は予期せぬマージコミット生成を防ぐ最善策。
• 共有ブランチへの `--force` push は厳禁。代わりに `git push --force-with-lease` を使うと、未取得コミットの上書きを防止できる。コンフリクト発生時は `git rebase --abort` して人間に委ねるのが自動化の正解。

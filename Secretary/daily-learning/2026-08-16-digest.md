**cronとPATH管理**
• cronジョブはユーザーの`.zshrc`を読まないため、デフォルトPATHは`/usr/bin:/bin`のみ。`/usr/local/bin`や`~/.nvm/bin`等はすべて消えるため、`claude`や`node`等のコマンドがexit 127で無音終了する。
• 3段階対策：①crontabの先頭に`PATH=/usr/local/bin:/usr/bin:/bin`を追記、②スクリプト内で`export PATH="..."`を明示、③コマンドはフルパス（`/usr/local/bin/claude`等）で指定。重ねて使うのが最も確実。
• macOSではcronよりlaunchdが推奨。plistの`EnvironmentVariables`キーで完全な環境変数を設定でき、スリープ中にスキップしたジョブも復帰時に実行されるため自動化の信頼性が高い。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e`だけでは不十分。`if`/`while`/`&&`/`||`の条件式内では発火せず、`((count++))`のような算術展開も初回ゼロで終了するなど、意図せぬ無音終了が頻発する。
• 推奨基盤は`set -Eeuo pipefail`の4セット：`-E`でERRトラップを関数内に継承、`-u`で未定義変数エラー化、`-o pipefail`でパイプライン途中の失敗を確実にキャッチ。
• `trap 'on_error $LINENO' ERR`でエラー行番号をログに残し、`trap cleanup EXIT`でテンポラリファイルのクリーンアップを保証するのが本番スクリプトの標準構成。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forward エラーの根本原因は「リモートに自分のローカルが持っていないコミットが存在する状態でpushしようとする」こと。自動化スクリプトでは`cp → pull → commit → push`の順序ミスで頻発する。
• 正しい順序は必ず`pull → ファイル操作 → commit → push`。`git pull --rebase`でローカルコミットをリモートの上に積み直してから操作することで、unstaged changesによるrebaseブロックを回避できる。
• `git config --global pull.rebase true`でデフォルトをrebaseに設定しておくと、`git pull`だけで安全なリベースが走る。pushは`--force-with-lease`を使うと誤って他者のコミットを上書きするリスクを防げる。

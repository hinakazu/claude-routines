**cronとPATH管理**
• cronジョブはユーザーの `.zshrc` や `.bash_profile` を読み込まず、最小限のPATHしか持たない。スクリプト冒頭で `PATH=/usr/local/bin:/usr/bin:/bin:$HOME/.local/bin` のように明示的に定義するのが最もシンプルで確実な解決策
• crontab内での変数展開は機能しない（`PATH=$HOME/bin:$PATH` は動かない）。値はリテラル扱いで、引用符も文字として扱われる
• デバッグには `env -i HOME=$HOME /bin/bash -c 'コマンド'` でcron環境を再現するのが有効。`/etc/environment` からはPATH以外の変数のみ引き継がれる点も注意
• macOSのlaunchdでは plist の `EnvironmentVariables` キーでPATHを指定可能。launchdはスケジュール実行だけでなく、ネットワーク変更・ログインイベントトリガーや自動再起動（KeepAlive）も提供する

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -euo pipefail` をスクリプト冒頭に置くのが2026年現在の定石。`-u` は未定義変数を検知し、`pipefail` はパイプライン途中の失敗を捕捉する
• `set -e` には盲点がある：`&&`/`||`/`!` チェーン内のコマンド失敗では発動しない。`foo=$(failing_cmd)` もコマンド置換内の失敗を検出しない（終了コードを捨てる）
• ERRトラップに `$LINENO` と `$BASH_COMMAND` を渡すことで「何行目の何が失敗したか」をログに残せる。`set -E` も合わせて設定しないと関数やサブシェル内でトラップが継承されない
• EXITトラップでクリーンアップを実行すればエラー終了時も一時ファイルを確実に削除できる。算術演算 `((count--))` が0を返すと非ゼロ終了になるため `|| true` を付ける

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトでの基本順序は「fetch → integrate（rebase/merge） → commit → push」。`cp` などのファイル変更前に `git pull --rebase` を実行することで unstaged changes によるrebaseブロックを防ぐ
• `git config --global pull.rebase true` をグローバル設定に入れておくことで、`git pull` が常にrebaseモードで動作する。複数箇所からpushが発生するリポジトリで特に有効
• rebase中にコンフリクトが発生した場合は `git rebase --abort` で中断してエラーで終了させる設計が重要。サイレントにforce pushするのは最悪のパターン
• force pushが避けられない場合は `--force-with-lease` を使う（`--force` はリモートの変更を上書きするリスクがある）。共有ブランチへのforce pushは禁止

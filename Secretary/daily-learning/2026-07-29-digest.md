**cronとPATH管理**
• cronジョブはユーザーのシェル設定（.zshrc/.bash_profile）を読み込まないため、/Applications/cmux.app/Contents/Resources/bin 等のカスタムPATHが未登録となりexit 127でサイレント失敗する。crontabファイルの冒頭で`PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/path/to/custom/bin`のように明示的にフルパスで記述するのが確実な対策。
• デバッグの鉄則：cron内で`env > /tmp/cron-env.txt`、シェル内で`env > /tmp/shell-env.txt`を実行して2つを比較すると、何が欠けているか即座に判明する。
• macOSでは2025年以降、Appleが公式にlaunchdを推奨しており、cronよりもSIPに適合し、スリープからの復帰後も実行を再開できる。LaunchAgents（~/Library/LaunchAgents/*.plist）で`<EnvironmentVariables>`タグ内にPATHを記述することで安定動作が保証される。

**`set -e` のサイレント終了とエラーハンドリング設計**
• set -e 単体では「いつ終了したかわからない」問題が残る。正しい組み合わせは`set -eEuo pipefail`＋`trap 'echo "Error at line $LINENO, exit code $?" >&2' ERR`で、エラー発生行番号とexit codeをstderrに記録できる。
• 重要な落とし穴3つ：①`if`条件内・`||`/`&&`の右辺のコマンドは set -e が効かない ②`((i++))` が0を返すとスクリプト終了 ③関数内のエラーはデフォルトでERRトラップを継承しない（`set -E`追加が必要）
• `set -E`（errtrace）を追加するとサブシェル・関数内にもERRトラップが伝播し、複雑なスクリプトでのデバッグが大幅に容易になる。2023年のShellCheck調査では、この組み合わせを使わない本番スクリプトの60%超でサイレントなデータ消失が発生していた。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forwardエラーはローカルとリモートが分岐した状態（リモートに自分にないコミットがある）で発生する。自動化スクリプトで「変更 → commit → pull → push」の順序を踏むと、unstaged changesがある状態でrebaseが走りブロックされる。正しい順序は必ず「pull → 変更 → commit → push」。
• `git pull --rebase origin main`を使うとマージコミットを作らずに線形履歴を保てる。競合が起きた場合は`git add <file>`→`git rebase --continue`で解消できる。
• 自動化スクリプトでの安全策：変更前に`git stash -u`で未コミット変更（untracked含む）を退避→pull→stash pop→commit→pushの順序にすると、どのタイミングで呼び出しても安全に実行できる。

**cronとPATH管理**
• cronジョブはユーザーの.zshrc/.bashrcを読み込まないため、PATH は /usr/bin:/bin のみになる。スクリプト冒頭で `export PATH=/usr/local/bin:/usr/bin:/bin:$HOME/...必要なパス...:$PATH` のように明示指定するのが最も確実。
• macOSのlaunchdではplistの `EnvironmentVariables` キーでPATHを指定する。現代のmacOS（Sequoia以降）ではcronが実質動作しない報告もあり、launchd移行が推奨される。
• デバッグは `* * * * * env > /tmp/cron-env.output` でcron環境を書き出し、ターミナルの `env` 出力と差分を確認するのが効率的。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` 単体では「パイプラインの途中の失敗」「`$(...)` コマンド置換内の失敗」「`if` や `&&/||` 式内の失敗」を捕捉できない。`set -euo pipefail` をセットで使うことで未定義変数とパイプ失敗も検出できる。
• `trap 'echo "Error on line $LINENO: exit $?" >&2' ERR` をスクリプト冒頭に置くと、失敗した行番号と終了コードをログに残せる。`set -e` だけでは原因特定が困難なため必須の対策。
• `((count--))` のような算術式はカウンタが0になると終了コード1を返し `set -e` がトリガーされる。`((count--)) || true` で回避できる。

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトでは `git pull --rebase --autostash` を使うことで、unstaged changes がある状態でも rebase をブロックされず、変更はstash→rebase→pop の順で自動処理される。
• CIでは `git pull --ff-only`（またはgit config `pull.ff=only`）を設定し、fast-forwardできない場合は明示的に失敗させる方が安全。divergenceを隠蔽せず早期検出できる。
• 操作順序のベストプラクティスは `git stash -u → git pull --rebase → git stash pop → git add → git commit → git push`。スクリプトでは `git status --porcelain` でdirty treeを事前チェックし、汚れがある場合は処理を中断するフェイルファスト設計が推奨される。

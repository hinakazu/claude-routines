**cronとPATH管理**
• cronジョブは `.zshrc` / `.bash_profile` を読まないためPATHは `/usr/bin:/bin` のみ。`/usr/local/bin` や独自バイナリはcrontab先頭で `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin` と明示する。
• `PATH=$PATH:/custom/path` 形式はcron実装によって変数展開されず、PATHが空文字になるケースがある。絶対パス記述かラッパースクリプト内でのexportが安全。
• macOS限定: launchd plistでは `<key>EnvironmentVariables</key>` に辞書形式で環境変数を明示でき、複雑な環境を持つ常駐型ジョブにはcronよりlaunchdが推奨。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は `if cmd; then` の条件部・`cmd && ...` / `cmd || ...` の左辺・パイプライン最終以外のコマンドでは**発動しない**。これらのコンテキストで失敗が静かに無視される。
• 推奨パターン: `set -euo pipefail` + `trap 'on_error $LINENO' ERR`。`-E` オプション追加でERRトラップがサブシェル・関数にも継承され、失敗行番号と終了コードをログに残せる。
• クリーンアップには `trap 'cleanup' EXIT` を使う。異常終了・シグナル割り込みどちらでもEXITは発火するため、一時ファイル削除やロック解放を確実に実行できる。

**git non-fast-forward と自動化スクリプトでの操作順序**
• non-fast-forwardはリモートに自分のローカルにないコミットがある際に発生。自動化では `git fetch → git rebase → 変更適用(cp等) → commit → push` の順を守る。変更適用を先にするとrebaseがunstaged changesを検出してブロックされる。
• `git config --global pull.rebase true` で常にrebaseモードにしておくとマージコミットが生成されないクリーンな履歴を保てる。スクリプト内では `git pull --rebase origin main` と明示的に書くほうが意図が明確。
• force pushは履歴破壊リスクがあり自動化スクリプトでは禁忌。non-fast-forwardが解消できない場合は通知を出して人手に委ねる設計にする。

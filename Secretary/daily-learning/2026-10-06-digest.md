**cronとPATH管理**
• cronジョブはユーザーのシェル（.zshrc等）を読み込まないため、PATH は `/usr/bin:/bin` 程度しかない。`claude`・`node`・`python` などを名前だけで呼ぶとexit 127でサイレント失敗する。
• 解決策3選：①crontabの先頭に `PATH=/usr/local/bin:/usr/bin:/bin:...` を明示 ②スクリプト内でフルパスを使う ③wrapper scriptでPATHを初期化してから本体を呼ぶ
• デバッグはcron内で `env > /tmp/cron-env.txt` を実行し、cronが認識している環境を可視化するのが最速。
• macOSではcronは非推奨で、**launchd**（plistでEnvironmentVariablesを宣言できる）が公式の後継。スリープ/ウェイク時のジョブ取りこぼしも launchd の方が堅牢。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は `if`/`elif` 条件式・`&&`/`||` チェーンの非末尾・コマンド置換 `$(...)` 内では発動しない。「安全に見えてデバッグを難しくする諸刃の剣」。
• 推奨は `set -Eeuo pipefail`：`-E` でERRトラップをサブシェル・関数に継承、`-u` で未設定変数を即エラー化、`-o pipefail` でパイプライン内の失敗を伝播。
• `trap 'echo "ERR at line $LINENO: $BASH_COMMAND (exit $?)" >&2' ERR` を冒頭に置くと、`set -e` が効かない文脈でも失敗をログに残せる。
• クリーンアップには `trap 'cleanup_func' EXIT` を必ず追加し、予期しない終了時にも一時ファイル等を回収する設計が定石。

**git 自動化スクリプトの操作順序（non-fast-forward 問題）**
• 正しい順序は `git pull --rebase` → ファイル修正 → `git add/commit` → `git push`。修正前にpullしないと、rebase時にunstagedな変更がブロック要因になる。
• スクリプトが複数箇所から同じリポジトリにpushする場合は、pushの直前にも `git pull --rebase` を入れる「二重pull」パターンが競合を防ぐ。
• `git pull --rebase` でコンフリクトが発生した場合は `git rebase --abort` で中断し、手動解決後に再試行する安全策を自動化スクリプトにも組み込むこと。
• CI/CDではpre-pushフックに `git fetch origin && git merge-base --is-ancestor HEAD origin/main` チェックを入れると、out-of-dateなpushをブロックできる。

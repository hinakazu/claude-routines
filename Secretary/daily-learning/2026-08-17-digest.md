**cronとPATH管理**
• cronはユーザーの.zshrc/.bashrcを読み込まないため、デフォルトPATHは `/usr/bin:/bin` のみ。Homebrewや独自ツールのパスが通らず `exit 127` でサイレント終了する。対策はcrontabの先頭か、ラッパースクリプト冒頭で `PATH=/usr/local/bin:/usr/bin:/bin:/opt/homebrew/bin` を明示的に記述すること。
• macOSでは `cron` はAppleに非推奨扱いで、`launchd` への移行が推奨されている。launchdはplistファイルで環境変数をジョブ単位で宣言的に設定でき、スリープ中にトリガー時刻を過ぎても起動後に実行してくれる（cronはスキップ）。
• ラッパースクリプト方式が最もテストしやすい：環境設定のみを行うwrapperをcronから呼び出し、本体スクリプトは独立してテスト可能な状態に保つ。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は `||`/`&&` チェーン、`if/elif` の条件部分、パイプライン中間コマンド、サブシェル内では発動しない。例えば `call && true` は失敗しても終了しないが `true && call` は終了する、という非直感的な挙動がある。
• 2026年のベストプラクティスは `set -euo pipefail` の3点セット。`-u` で未定義変数のタイポを検出、`-o pipefail` でパイプライン中間コマンドの失敗も検出できる。
• `trap ERR` に `set -E`（errtrace）を組み合わせることでサブシェル内にもERRトラップが継承される。`trap cleanup EXIT` を追加すれば、エラー終了時も確実にクリーンアップ実行。ログには `echo "ERROR at line $LINENO, exit code $?"` のように行番号と終了コードを記録するのが鉄則。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forwardエラーの根本原因は「ローカルのHEADがリモートのHEADの祖先でない状態でpushしようとする」こと。自動化スクリプトでは `pull → 変更作業 → commit → push` の順序を徹底する。commitしてからpullすると unstaged changesでrebaseがブロックされる罠にはまる。
• `git push --force-with-lease` は `--force` より安全。リモートのHEADが期待値と異なれば自動的に失敗するため、他人のコミットを誤って上書きするリスクがない。rebase後のpushでは必ずこちらを使う。
• 自動化では pre-push hook で `git fetch && git rebase origin/main` を自動実行する仕組みが有効。Huskyなどで CI強制も可能。ブランチ戦略（GitHub Flow）でmainとの同期をこまめに行うことが最も根本的な予防策。

**cronとPATH管理**
• cronはユーザーの`.zshrc`/`.bashrc`を一切読み込まないため、PATH環境変数が大幅に削られた最小限の状態で実行される。`/etc/environment`でPATHを追加しても、cronはそのPATH変更を無視するという罠がある（他の変数は反映される）。
• 対策は2層構造が推奨: (1) crontabの先頭に`PATH=/usr/local/bin:/usr/bin:/bin:/your/custom/bin`と明示 + (2) `SHELL=/bin/bash`指定。(3) シークレット類は600パーミッションの別ファイルに分離してスクリプト内で`source`する。
• デバッグの鉄則: `* * * * * env > /tmp/cron-env.txt`を一時的に仕込んでcron環境をダンプし、インタラクティブシェルの`env`と差分を比較する。PATH・SHELL・LANG・TZの不一致がほぼ原因。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e`には「発火しない例外」が4つある: `if`条件部、`!`否定、`&&`/`||`チェーン内、コマンド置換`$(...)`内。これらでは失敗してもスクリプトが続行するため、想定外の無音通過が起きる。
• ERRトラップは`set -e`が発火しない箇所では同様に発火しない。さらに関数内でERRトラップを継承させるには`set -E`（大文字）が必要。
• 推奨の基底設定: `set -euo pipefail` + `trap 'echo "ERR: line $LINENO cmd=$BASH_COMMAND" >&2' ERR` + `trap cleanup EXIT`の3点セット。意図的に失敗を許容するコマンドは`cmd || true`または`set +e; cmd; set -e`で明示的に囲む。

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトでgit操作を組み合わせるとき「作業→commit→push」の順序はnon-fast-forwardで失敗する。正しい順序は`git pull --rebase`→ファイル変更→`git add`→`git commit`→`git push`。
• pushが拒否された場合のリトライ戦略: `git pull --rebase && git push`をループで最大N回繰り返す。同一リポジトリへの複数箇所からのpushが競合するシナリオ（CIと手動など）では特に有効。
• unstaged changesがある状態でrebaseを実行するとブロックされる。`git stash -u`→`git pull --rebase`→`git stash pop`の順序でunstagedも含めて安全に取り込める。

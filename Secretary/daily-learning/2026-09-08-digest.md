**cronとPATH管理**
• cronジョブは最小限のPATH（/usr/bin:/bin のみ）で動作し、ユーザーの .zshrc や .bashrc は読み込まれない。/opt/homebrew/bin など独自パスに置かれたコマンドはすべてexit 127でサイレント失敗する。
• 最も確実な対策はスクリプト冒頭で `PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin` と明示すること。crontab自体に `PATH=` を記述してもよいが、`$PATH` のような変数展開は一部のcron実装では機能しない。
• macOSではAppleがcronを非推奨とし、launchdが公式推奨。launchdではplistファイルにEnvironmentVariablesとして環境変数を宣言でき、シェル環境に依存しない宣言的なPATH管理ができる。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は失敗したコマンドでスクリプトを即終了させるが、失敗原因がログに残らないためデバッグを困難にする。`(( i++ ))` が0を返した場合も終了する、サブシェルにはデフォルトで伝播しないなど、直感に反する挙動が多い。
• 本番スクリプトでは `set -eEuo pipefail` を先頭に置き、`trap 'echo "Error at line $LINENO: $BASH_COMMAND (exit $?)" >> /var/log/myscript.err' ERR` でエラー行・コマンド・終了コードを記録する設計が標準パターン。
• `trap cleanup EXIT` で正常終了・異常終了両方の後処理を保証する。ERRトラップをfunctionやサブシェルに継承するには `set -E`（errtrace）が必要。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forward エラーは「ローカルにないリモートコミットが存在する状態でpushしようとした」ときに発生する。複数箇所からpushが行われるCI botや自動化環境では常時発生するリスクがある。
• 自動化スクリプトでの安全な操作順序は「stash → pull --rebase → (stash pop) → commit → push」。変更を先にコミットしてからpullするとリベースが汚れた作業ツリーでブロックされる。
• `git config --global pull.rebase true` でデフォルト戦略をrebaseにすると線形履歴を保ちやすく、自動化スクリプトとの相性が良い。失敗したpushに対して `git pull --rebase && git push` でリトライするパターンも標準的。

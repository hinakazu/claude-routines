**cronとPATH管理**
• cronジョブはユーザーの `.zshrc` や `.bashrc` を読み込まないため、デフォルトのPATHは `/usr/bin:/bin` のみ。`/opt/homebrew/bin` や `/usr/local/bin` に置かれたツール（`claude`、`node`など）は見つからずexit 127で無音終了する。
• 解決策は3つ：(1) crontab冒頭に `PATH=/usr/local/bin:/opt/homebrew/bin:/usr/bin:/bin` と明示する、(2) スクリプト冒頭でexportする、(3) コマンドをフルパス指定する。
• macOSではcronは非推奨。`launchd`（plistファイル）が推奨だが、こちらもシェルを介さないため`EnvironmentVariables`キーでPATHを明示するか、`/bin/sh -c`経由で実行する必要がある。
• デバッグ方法：`env > /tmp/cron_env.txt`を一時ジョブとして実行し、実際のcron環境変数をダンプして確認する。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e`（errexit）は強力だが、条件式・論理演算子・パイプライン・コマンド置換では発動しない例外が多い。`||`でつなぐと失敗がマスクされ、`$(cmd)`内の失敗も無視される（Bash 4.4以降は`inherit_errexit`で解消可）。
• `local var=$(cmd)`は特に危険：`local`自体の終了コードが0になるためerrexitが発動しない。宣言と代入を分けること（`local var; var=$(cmd)`）。
• 推奨strictモードは`set -Eeuo pipefail`。`-E`でERRトラップを関数内でも継承、`-u`で未定義変数エラー、`-o pipefail`でパイプ途中の失敗を捕捉。
• ERRトラップでの行番号出力：`trap 'echo "Error on line $LINENO in $(caller)"' ERR`でデバッグ効率が大幅向上。

**git non-fast-forward と自動化スクリプトでのrebase操作順序**
• non-fast-forwardエラーはリモートにローカルにないコミットが存在する場合に発生。自動化スクリプトで複数箇所からpushする場合に頻発する。
• 正しい操作順序は「fetch → 作業ファイル変更 → commit → rebase → push」。pull前にファイルを変更すると`git rebase`がunstaged changesをブロックする。
• `git pull --rebase --autostash`を使うと作業中ファイルを一時退避しながらrebaseできCI/CDでの自動化に有用。グローバル設定`git config --global pull.rebase true`でデフォルト化も可。
• force pushが必要な場合は必ず`--force-with-lease`を使う。`--force`はリモートの他者コミットを上書きするリスクがあるが、`--force-with-lease`はローカルが最新を取得済みの場合のみ許可する安全なオプション。

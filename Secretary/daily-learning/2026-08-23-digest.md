**cronとPATH管理**
• cronはデフォルトで `/usr/bin:/bin` という極めて限定的なPATHでジョブを実行する。`.zshrc`や`.bashrc`は読み込まれないため、Homebrewや `/opt/homebrew/bin` などカスタムパスが一切使えず、コマンドがexit 127でサイレント終了する
• 解決策①: crontabファイルの先頭に `SHELL=/bin/bash` と `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/opt/homebrew/bin` を明示的に設定する
• 解決策②: スクリプト冒頭でPATHを明示設定し、コマンドには絶対パスを使う。macOSのlaunchdでは `EnvironmentVariables` キーにPATHを記載し、スリープ復帰後の取りこぼしも自動実行される点がcronより優れている

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は `if`条件部・`&&`/`||`チェーンの途中・コマンド置換（`out=$(false)`）では機能しないという重大な落とし穴がある。`true && call` の形で書くと失敗してもスクリプトが継続してしまうケースがある
• 推奨パターンは `set -euo pipefail` ＋ `trap 'handle_error "$?" "${BASH_COMMAND}"' ERR` の組み合わせで、90%のバグを事前防止できる。`set -E`（errtrace）を加えることでERRトラップがサブシェル・関数にも継承される
• エラーハンドラに失敗コマンド名（`$BASH_COMMAND`）・行番号（`$LINENO`）・終了コード（`$?`）をログ出力する仕組みを入れると、サイレント終了の原因が即座に特定できる

**git non-fast-forward push と rebase の操作順序**
• non-fast-forwardエラーは「最後のpull以降にリモートへ別のpushが入った」状態で発生する。CI/CDボット・別セッション・Dependabotが同じ分に自動コミットすることが多く、自動化スクリプトで特に踏みやすい
• 自動化スクリプトの正しい操作順序は `git pull --rebase` → ファイル操作（cp等）→ `git add` → `git commit` → `git push`。変更前にpullしないとunstaged changesがあってrebaseがブロックされる
• `git config --global pull.rebase true` でデフォルトをrebaseにしておくと将来のミスを予防できる。rebase中にコンフリクトが出たら `git add` 後に `git rebase --continue` で再開

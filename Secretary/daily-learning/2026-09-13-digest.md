**cronとPATH管理**
• cronはユーザーの`.zshrc`や`.bash_profile`を読まず、`/usr/bin:/bin`程度の極小PATHで起動するため、`/usr/local/bin`や`/Applications/xxx/bin`にあるコマンドはexit 127で無音失敗する。スクリプト冒頭で `PATH=/usr/local/bin:/usr/bin:/bin` を明示するか、全コマンドをフルパスで書くのが最も確実な対策。
• macOSでは`launchd`（plistファイルで設定）がcronの現代的代替で、スリープ中にスキップされたジョブをウェイクアップ後に実行する。`~/Library/LaunchAgents/`にplistを置き、`EnvironmentVariables`キーでPATHを明示指定できる。
• ラッパースクリプトパターン（環境変数を設定するシェルを経由して本体を呼ぶ）は最もポータブルな解決策で、手動実行とcron実行で同一のテストが可能。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e`は「非ゼロ終了で即abort」するがログを残さず消えるため原因特定が困難。`set -euo pipefail`をセットにして使い、パイプ中のエラーも拾う。`(( i++ ))`など算術式が0を返してもabortするため`(( i++ )) || true`と回避が必要。
• `trap 'echo "ERROR at line $LINENO: $BASH_COMMAND" >&2' ERR`でエラー発生行番号とコマンドをstderrに記録できる。`set -E`（errtrace）を追加すると関数・サブシェル内のERRトラップも継承される。
• ShellCheckによる静的解析と`bash -x`トレース実行を組み合わせるとデバッグが格段に速くなる。エラーログは`2>> /var/log/myscript.err`でファイルに落とすと後追いが容易。

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトで `cp → commit → pull → push` の順を踏むと、pullが"unstaged changes"にぶつかってrebaseがブロックされる。正しい順序は `pull（またはfetch+rebase）→ ファイル操作 → add → commit → push`。
• `git pull --rebase`はリモートの変更の上にローカルコミットを積み直しマージコミットを生まない。複数箇所からpushが走る場合は`--force-with-lease`付きのpushと組み合わせて競合を安全に検出する。
• CIや自動化での安全なgit操作パターン：`git fetch` → `git log HEAD..origin/main`で新コミット有無を確認 → 必要なら`git rebase` → `push`のフロー。GitPythonを使えばPython側でこの状態機械を明示的に制御できる。

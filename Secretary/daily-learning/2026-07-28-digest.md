**cronとPATH管理**
• cronジョブは `PATH=/usr/bin:/bin` のみで起動し、`~/.zshrc` や `~/.bashrc` は読み込まれない。`/Applications/cmux.app/Contents/Resources/bin` のような独自パスはcrontabの先頭で明示的に宣言しなければ、コマンドはexit 127でサイレント失敗する。
• `PATH=$PATH:/custom/path` のような変数展開はcron実装によっては動かず、文字通り `$PATH` という文字列になる危険がある。完全パスを直接記述すること（例: `PATH=/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin:/Applications/cmux.app/Contents/Resources/bin`）。
• macOSではAppleが推奨するlaunchdへの移行が本質的解決策。launchdはEnvironmentVariablesでPATHを宣言し、スリープ中にスキップしたジョブをシステム起動後に検知して自動実行する。Apple Silicon Macでは `/opt/homebrew/bin` も必ず含める。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` 単体は「失敗したら終了」するが終了理由をログに残さない。本番スクリプトでは `set -euo pipefail` をセットで使い、`-u` で未定義変数をエラー扱いし、`-o pipefail` でパイプライン内の失敗も検知する。
• `trap "handler_function" ERR` でエラー発生時のハンドラを登録し、失敗コマンド・行番号・終了コードをログに書く。`trap "cleanup" EXIT` をセットにすれば、正常終了・エラー終了・Ctrl+C のいずれでもクリーンアップが走る（リソースリーク40%削減の報告あり）。
• `|| true` パターンは意図しないエラーまで隠すため使い所を限定すること。コマンド置換（`$(...)`）内のエラーは `set -e` で即終了しないケースがある点も要注意。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forwardエラーは「ローカルにもリモートにも相手が知らないコミットがある」状態（ブランチ分岐）で発生する。自動化スクリプトで `cp → commit → pull → push` の順にすると、pull時にunstaged changesが残っておりrebaseがブロックされる。正しい順序は `pull → (変更処理) → commit → push`。
• `git pull --rebase` はローカルコミットを一時退避し、リモートの変更を取得してからローカルコミットを上に再適用する。マージコミットが生成されず履歴が線形に保たれるため、自動化スクリプトに適している。
• 予防策として `--ff-only` フラグでfast-forwardのみを許可し、意図しないマージコミットを完全に防ぐ。rebaseでコンフリクトが発生した場合は手動解決後に `git rebase --continue` が必要で、スクリプトが止まる設計にしておくこと。

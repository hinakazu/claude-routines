**cronのPATH管理とmacOSのlaunchd移行**
• cronはユーザーの.zshrcを読み込まず、`/usr/bin:/bin`のみのミニマルなPATHで動作するため、Homebrewやカスタムバイナリ（例：`/Applications/cmux.app/Contents/Resources/bin`）がPATH未登録になる。解決策はcrontabファイルの先頭に`PATH=`を明示的に書くか、ラッパースクリプトで`export PATH`を宣言すること。
• macOSではAppleがlaunchdへの移行を10年以上推奨しており、cronでは対処困難な「スリープ復帰後のジョブ再実行」「イベントトリガー」もlaunchdなら可能。Apple Silicon（M系）では`EnvironmentVariables`に`/opt/homebrew/bin`を明示的に追加することが必須。
• デバッグ方法：crontabの全コマンドに`>> /tmp/cron.log 2>&1`を追加して標準エラーをキャプチャし、まず`which <command>`でPATH解決の有無を確認する。

**`set -e`のサイレント終了とtrap ERRによるエラーハンドリング**
• `set -e`はif/elif条件部・&&/||チェーン・パイプのラスト以外では発動しない。特に`out=$(false)`のようなコマンド置換の中では継承されない点が最大の罠。`call && true`はerrexitが発動しないが`true && call`は発動するという非直感的な挙動がある。
• 推奨パターンは`set -eE`（errexit + errtrace）と`trap 'handle_error $? $LINENO' ERR`の組み合わせ。`-E`を使うことでサブシェル・関数内でもERRトラップが継承される。コマンド置換内のerrexitを継承させるには`inherit_errexit`も追加する。
• ベストプラクティス：エラーハンドラ関数でスクリプト名・コマンド・行番号・終了コードをすべてログに記録する。`trap cleanup EXIT`で一時ファイル削除やプロセス終了の後処理を確実に行う。

**git non-fast-forward pushとrebaseの正しい操作順序**
• 自動化スクリプトでの黄金ルール：`git pull --rebase`を必ずcommit前・add前に実行すること。`cp → commit → pull → push`の順序はnon-fast-forwardエラーの原因になる。正しい順序は`pull → cp → add → commit → push`。
• `git pull --rebase`はローカルコミットをリモートの最新コミットの上に再適用するため、マージコミットが生まれず履歴がリニアに保たれる。ただしunstaged changesが残った状態でrebaseするとabortされるので、`git stash`で一時退避してからpullするか、必ずcommit済みの状態を保つ必要がある。
• 自動化スクリプトでの安全パターン：`git fetch origin <branch>` → `git rebase origin/<branch>`で段階的に実行し、conflictが発生した場合は`git rebase --abort`でスクリプトを停止してSlackに通知する。force pushは必ず`--force-with-lease`のみ使用（チームメンバーの変更を上書きしない）。

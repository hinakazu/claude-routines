**cronとPATH管理**
• cronは `/usr/bin:/bin` 程度の最小限PATHで起動し、`.zshrc`や`.bash_profile`を読み込まない。`/usr/local/bin`や`/opt/homebrew/bin`（Apple Silicon Mac）が未登録になり、`claude`や`brew`系コマンドがexit 127でサイレント失敗する。
• 対策は3層：①crontab冒頭に `SHELL=/bin/bash` + `PATH=...` を宣言、②スクリプト冒頭の`#!/bin/bash`直後にPATHを上書き、③コマンドは絶対パスで記述。
• macOSでは`cron`の代替として`launchd`が推奨。plistの`EnvironmentVariables`でジョブごとにPATHを宣言でき、Macスリープ中のジョブをスキップせず起動後に実行する点でcronより信頼性が高い。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e`は`if`条件式・`&&`・`||`・`!`で修飾されたコマンドでは発火しない。これらのコンテキストでの失敗は無音で続行されるため、デバッグが困難になる。
• `((count++))` の算術式は初回に0（偽）を返すため`set -e`環境でスクリプトが即終了する罠がある。`count=$((count + 1))`か`((count++)) || true`で回避する。
• 推奨パターンは冒頭に `set -euo pipefail` を置き、`trap 'echo "Error on line $LINENO: $BASH_COMMAND" >&2' ERR` を組み合わせること。失敗行・失敗コマンドがログに残り原因特定が容易になる。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forwardエラーは「リモートブランチがローカルのコミット履歴の祖先でない」ときに発生する。複数箇所からpushが発生する自動化スクリプトで頻出。
• 安全な操作順序は `git fetch origin` → `git merge origin/<branch>`（または`git pull --rebase`）→ ファイル変更 → `git add + commit` → `git push`。pull前に変更をワーキングツリーに置くとrebaseがブロックされる。
• `git pull --rebase` はローカルコミットを巻き戻してリモート変更を先に適用し、その後ローカルコミットをリプレイするため履歴が線形に保たれる。共有ブランチへのpush済みコミットのrebaseは厳禁。

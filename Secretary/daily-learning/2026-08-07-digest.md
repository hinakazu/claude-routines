**cronとPATH管理**
• cronジョブは`.zshrc`/`.bashrc`を読み込まない最小環境で動作するため、`/usr/local/bin`や`/opt/homebrew/bin`（Apple Silicon Mac）が未登録になる。スクリプトがターミナルで動いてもcronで無音終了する主因はこれ。
• 最も確実な対策は**crontabの先頭行で`PATH=`を明示**すること（例：`PATH=/usr/local/bin:/usr/bin:/bin:/opt/homebrew/bin`）。スクリプト内では絶対パスを使うのも有効。
• デバッグには`* * * * * env > /tmp/cron-env.txt`を一時追加してcronの実際の環境を確認する方法が実用的。
• macOSではcronはdeprecated。launchdのplistファイルで`EnvironmentVariables`キーを使いPATHを明示するのが正式対応。`EnvironmentVariables`ブロックに`PATH`を書けばdaemon起動時に適用される。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e`の3大落とし穴：①`((count++))` が0を返すと即終了（算術）、②パイプラインは最後のコマンドの終了コードのみ採用（`set -o pipefail`で解消）、③条件式（`if`/`&&`/`||`）内のコマンドは`set -e`が効かない。
• 推奨テンプレートは`set -euo pipefail`に`set -E`を加え、functionやサブシェルにもERRトラップを継承させること。`trap 'echo "ERR line $LINENO exit $? cmd: $BASH_COMMAND" >> /tmp/err.log' ERR`でサイレント失敗をログに残せる。
• `set -u`（未定義変数をエラーに）も組み合わせると、タイプミスによる変数名誤りも検出できてスクリプト品質が上がる。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forwardエラーの根本原因はリモートが先行した状態でpushしようとすること。自動化スクリプトの正しい順序は**pull → 変更 → commit → push**。変更してからpullするとunstaged changesがrebaseをブロックする。
• unstaged changesがある状態で`git pull --rebase`が必要な場合は、`git stash push` → `git pull --rebase` → `git stash pop`の3ステップ。Git 2.6以降は`git pull --rebase --autostash`で自動stash可能。`git config --global rebase.autoStash true`を設定しておくと常に自動stashが有効になる。
• `git stash pop`時にマージコンフリクトが発生する可能性があるため、スクリプトでは`pop`ではなく`apply`を使い、成功確認後に`git stash drop`するのが安全。

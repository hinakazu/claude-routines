**cronとPATH管理**
• cronジョブはユーザーの `.zshrc` / `.bashrc` を読み込まないため、`/Applications/cmux.app/Contents/Resources/bin` のようなカスタムパスが未登録になり `exit 127` でサイレント終了する。スクリプト冒頭で `export PATH=/usr/local/bin:/usr/bin:/bin:$PATH` を明示的に追加するのが最も安全な回避策。
• macOS Sequoia 以降では cron デーモン自体が動作しないケースが報告されており、代替として launchd の plist に `EnvironmentVariables` キーで PATH を設定する方式が Apple 公式の推奨。
• デバッグ手法：cronの実環境を `* * * * * env > /tmp/cron-env.txt` でダンプして対話シェルと差分を取るのが最速。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` の典型的な落とし穴は3つ：①`local var=$(cmd)` で `cmd` の失敗コードが隠れる（宣言と代入を分ける）、②パイプラインの途中の失敗が `set -e` だけでは検知できない（`set -o pipefail` を併用）、③`((count--))` が 0 を返すとき非ゼロ終了扱いになりスクリプトが止まる（`|| true` を付加）。
• 推奨する「Strict Mode」: `set -euo pipefail` を組み合わせ、`trap 'echo "ERROR at line $LINENO" >&2' ERR` で失敗箇所をログに残す。ERR トラップを関数内にも伝播させるには `set -E`（errtrace）が必要。
• `set -e` はサブシェル・コマンド置換では効果が弱い。Bash 4.4+ の `inherit_errexit` を設定するとサブシェルにも伝播するが、古い環境では使えないため明示的なエラーチェックが保険になる。

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトでの正しい順序は **pull → ファイルコピー → add → commit → push**。先にファイルを置いてから pull するとリモートの変更が unstaged changes を上書きできず rebase がブロックされる。
• `git pull --ff-only origin <branch>` を使うと fast-forward できない場合は即エラー終了し、意図しないマージコミットの混入を防げる。自動化スクリプトでは `--rebase` より `--ff-only` の方がトラブルが少ない。
• push が拒否された場合のリトライ戦略：`git fetch → git rebase origin/<branch> → git push` の順で再試行。コンフリクト発生時はスクリプトを止めてエラーログを残す（force push は厳禁）。

**cronとPATH管理**
• cronジョブはユーザーの `.zshrc` や `.bash_profile` を読み込まず、PATH は `/usr/bin:/bin` 程度しか設定されない。Homebrew等のツールは `/opt/homebrew/bin` にあるため、スクリプト冒頭で `export PATH="/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:$PATH"` を明示するか、crontab の先頭行に `PATH=...` を記述するのが確実。
• macOS では `cron` は Apple 非推奨であり `launchd` が後継。launchd はスリープ中に実行できなかったジョブをウェイクアップ後に再実行できるが、cron は無音でスキップする。重要な定期ジョブは launchd（`.plist` ファイル）への移行が安全。
• 絶対パスで実行ファイルを指定する（`/usr/local/bin/node` 等）と、PATH 問題を根本から回避できる。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` 単体では `if` 文・`||`/`&&` チェーン・サブシェル内のエラーを捕捉しない。スクリプト冒頭に `set -euo pipefail` を使い、`set -E`（errtrace）も追加することで関数・サブシェル内のエラーも `trap ERR` で受け取れる。
• エラー発生時に行番号・コマンドをログに残す定番パターンは `trap 'echo "ERROR: line $LINENO, exit $?" >&2' ERR`。これでサイレント終了がデバッグ可能な失敗に変わる。
• `trap cleanup EXIT` を合わせて使うと、一時ファイルやバックグラウンドプロセスのクリーンアップを確実に実行できる。失敗しても後続の状態が汚れない。

**git non-fast-forward push と rebase の操作順序**
• `git pull --rebase` はリモートの変更を取り込んだ上にローカルコミットを積み直し、マージコミット不要の線形履歴を保つ。自動化スクリプトでは `pull → ファイル操作 → add → commit → push` の順序が鉄則で、ファイル操作を先にすると unstaged changes で rebase がブロックされる。
• non-fast-forward エラーが起きた場合の解決手順は `git fetch origin` → `git merge origin/<branch>` または `git pull --rebase`。stash を使って未コミット変更を退避させてから pull する方法も有効（`git stash → pull → stash pop`）。
• CI/CD での git 自動化には `git config pull.rebase true` をリポジトリ設定として残しておくと、意図しないマージコミットを防げる。

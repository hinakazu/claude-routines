**cronとPATH管理**
• cronジョブは `/etc/environment` のPATHを無視するため、`/usr/local/bin` など通常のパスが未登録になりやすい。スクリプト冒頭で `PATH=/usr/local/bin:/usr/bin:/bin` のように明示的に指定するか、絶対パスを使うのが最も確実な対策。
• デバッグには `* * * * * env > /tmp/cron_env.txt` でcronの環境変数を丸ごとダンプする手法が有効。何が使えて何が使えないか一目瞭然になる。
• より堅牢な設計として「環境変数を一元管理するファイル（例: `~/.env_shared`）をスクリプト冒頭で `source` する」パターンがある。cronでもターミナルでも同じ環境を再現でき、設定の二重管理を防げる。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` の三大落とし穴：① `local var=$(cmd)` は `local` コマンドのexit statusで上書きされ、`cmd` の失敗が無視される → 宣言と代入を別行に分ける。② `((count--))` は結果が0のとき終了コード1を返し、スクリプトが予期せず中断する → `|| true` を添付。③ コマンド置換 `$(...)` 内の失敗は `set -e` では捕捉されない → `set -o inherit_errexit`（Bash 4.4+）で回避。
• `set -euo pipefail` をベースラインにしつつ、これを「完全な安全保証」と勘違いしないことが重要。多数の `|| true` が増え始めたらスクリプト設計を見直すサイン。
• `trap 'echo "Error at line $LINENO"' ERR` で失敗行番号をログに残すパターンが実用的。ERRトラップはサブシェルには伝播しないため、`set -E`（errtrace）を合わせて設定する必要がある。

**git non-fast-forward と rebase の操作順序**
• 自動化スクリプトでの鉄則は「裸の `git pull` を使わない」こと。`pull.rebase` や `pull.ff` のユーザー設定に動作が依存するため、CI環境や別マシンで意図しない挙動になりやすい。代わりに `git pull --rebase` または `git pull --ff-only` と明示フラグを使う。
• dirty worktree（未コミットの変更がある状態）でのpullには `git pull --rebase --autostash` が安全。pullの前後でstash/pop を自動的に行い、変更を保護してくれる。`git config rebase.autoStash true` で常時有効化も可能。
• 操作順序の原則：変更がある状態でpullすると衝突しやすい。自動化スクリプトでは `git fetch → git stash → git rebase origin/main → git stash pop` の明示的なシーケンスか、`--autostash` に任せることで予期しないブロックを回避できる。

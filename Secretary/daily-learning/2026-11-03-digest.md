**cronとPATH管理**
• cronジョブはユーザーの.zshrc/.bash_profileを読み込まず、最小限のPATH（/usr/bin:/bin程度）しか持たない。Homebrewや`/Applications/cmux.app/Contents/Resources/bin`等はデフォルトでは見えず、`claude`コマンドがexit 127でサイレント失敗する原因になる。
• 対策：crontabの先頭に`PATH=/usr/local/bin:/usr/bin:/bin:/path/to/tool`と**フルパスで**明示設定する（`PATH=$HOME/bin:$PATH`のような変数展開はcrontab内では使えない）。デバッグ時は`* * * * * env > /tmp/cron-env.txt 2>&1`を一時ジョブとして追加し、実際のcron環境を確認する。
• macOSではcronは非推奨でlaunchdが推奨（`~/Library/LaunchAgents/`のplistファイル）。launchdでも同様にPATHが制限されるため、plistの`EnvironmentVariables`キーにパスを追加が必要。「スクリプトが手動では動くのにlaunchdで動かない」はFull Disk Access権限が原因のこともある。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e`には重大な例外が3つある。①コマンド置換`$(...)`内の失敗は検知されない（`inherit_errexit`未設定時）。②`if`/`&&`/`||`の条件部分での失敗はexitしない。③`local var=$(cmd)`のように宣言ビルトインと組み合わせると終了コードがマスクされる（`local`は常に0を返す）。
• 推奨パターンは`set -Eeuo pipefail`＋`trap 'echo "Error at line $LINENO" >&2' ERR`＋`trap cleanup EXIT`の組み合わせ。`-E`フラグが重要で、これがないとERRトラップが関数・サブシェル内で継承されない。期待する失敗は`|| true`や一時的な`set +e`ブロックで明示的にハンドリングする。
• Bash FAQ（wooledge.org）は`set -e`自体に懐疑的で「自前でエラーチェックを書け」を推奨。実際には`set -Eeuo pipefail`と明示的ハンドリングの併用が2025〜2026年の主流。

**git non-fast-forward push と rebase の操作順序**
• 複数箇所からpushが発生するリポジトリで「unstaged changesがあるとrebaseがブロックされる」問題の正しい対処：`git pull --rebase --autostash`を使うとgitが自動でstash→rebase→stash popしてくれる。ただしGit v2.32.0でfast-forward時にautostashが無視されるリグレッションがあったため、バージョン確認が必要。
• 自動化スクリプトの推奨順序は①`git fetch origin`→②`git pull --rebase --autostash`→③exit codeとgit statusを確認→④commit→⑤push。pull.rebaseをglobal configに依存せず、`git -c pull.rebase=true pull`のようにスクリプト内で一時設定するとポータブルになる。
• autostash後のstash popが失敗する（untrackedファイルが競合する）ケースもあるため、`git pull --rebase --autostash`の終了コードを確認後、さらに`git status`で状態確認する二重チェックを推奨。`git checkout -- .`や`git clean -fd`を自動化に使うのは作業消去の危険があるため避ける。

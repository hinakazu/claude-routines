**cronとPATH管理**
• cronはユーザーの `.bashrc`/`.zshrc` を読み込まないため、PATHは `/usr/bin:/bin` 程度の最小限になる。`/Applications/cmux.app/Contents/Resources/bin` 等のカスタムパスは未登録となりexit 127で無音終了する。
• 解決策は3層: ①crontabファイル冒頭に `SHELL=/bin/bash` と `PATH=/usr/local/bin:/usr/bin:/bin:...` を明示、②スクリプト内で絶対パスを使用、③ラッパースクリプトで環境変数を集中管理。`/etc/environment` に書くとcron含む全プロセスに適用される。変数展開（`PATH=$PATH:...`）は一部のcron実装でサポートされないため完全パス記述が安全。
• デバッグ法: `env -i /bin/sh -c 'env'` でcronと同等の環境を再現し、スクリプトを手動テストする。`2>&1 | tee /tmp/cron.log` でエラーをキャプチャする。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は「失敗したら即終了」だが、`if`/`while` 条件式・`&&`/`||` チェーン・コマンド置換 `$(...)` の中では機能しない。`true && my_cmd` は動作し `my_cmd && true` は動作しないという非直感的な挙動が潜む。
• 推奨パターン: `set -eEo pipefail` + `trap 'handle_error "$?" "${BASH_COMMAND}"' ERR` の組み合わせ。`-E (errtrace)` によってERRトラップがサブシェルに継承され、`${BASH_COMMAND}` で失敗したコマンド名がログに残る。
• クリーンアップには別途 `trap cleanup EXIT` を設定する。`EXIT` トラップは正常・エラー終了どちらでも実行されるため、一時ファイルやバックグラウンドプロセスの後始末に確実。`set -e` だけに頼らず `trap ERR` との組み合わせが実運用上の信頼性を高める。

**git non-fast-forward push と操作順序**
• non-fast-forwardエラーは「リモートブランチがローカルの親コミットでない」状態で発生する。自動化スクリプトで複数箇所からpushすると起きやすく、根本原因は「pull前にファイル操作→commit」という順序ミス。
• 正しい順序: `git pull --rebase origin <branch>` → ファイルコピー・編集 → `git add` → `git commit` → `git push`。`pull --rebase` は履歴を線形に保ちつつリモートの変更を取り込み、マージコミットが生まれない。
• 防衛策: `git status --porcelain` でunstaged changesを事前検知してからrebase実行。pre-pushフックに `git fetch && git rebase origin/<branch>` を組み込むと自動化スクリプトのpushミスを防げる。

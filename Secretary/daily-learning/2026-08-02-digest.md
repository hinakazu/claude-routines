**cronとPATH管理**
• cronジョブは非ログイン・非インタラクティブシェルで動作するため `.zshrc` や `.bash_profile` が一切読み込まれず、Homebrew等の `/opt/homebrew/bin` や `/usr/local/bin` にある独自コマンドが全てexit 127（command not found）で無音終了する。解決策は①スクリプト冒頭で `PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin` を明示する、②crontab最上部に変数宣言する（`export`不要・使用不可）、③実行ファイルをフルパス指定する（`which claude` で確認）の3択。
• macOSでは **launchd** がcronの公式後継で、plistの `EnvironmentVariables` キーで `PATH` を宣言でき、スリープ中にスキップしたジョブを起動時に補完実行する機能もある。Apple Silicon環境では `/opt/homebrew/bin` の追加が必須。
• 本番自動化では「ラッパースクリプト方式」が最も安全：cronは短い `.sh` を呼ぶだけにし、そのスクリプト冒頭で環境変数を完全に宣言してから本体を呼ぶことで、設定の見通しが良くデバッグしやすくなる。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e`（errexit）は「コマンド失敗時に即終了」するが、`if` 条件式・パイプライン中間コマンド・コマンド置換 `$()` の中では発動しないという3大例外がある。`command && true` のように後続にtrueが続くだけで終了が抑制されるなど、動作が直感に反する場面が多い。
• 堅牢なスクリプトの定番は `set -eEuo pipefail` の4オプション組み合わせ：`-E`（errtrace）でERRトラップをサブシェル・関数内に継承、`-u` で未定義変数参照を即エラー化、`-o pipefail` でパイプライン途中の失敗も捕捉。さらに `trap 'echo "ERROR at line $LINENO"; exit 1' ERR` でエラー発生行番号をログに残す。
• デバッグには `FUNCNAME`・`BASH_LINENO`・`BASH_SOURCE` の3つのマジック配列と `caller` 組み込みコマンドでスタックトレースを出力できる。本番スクリプトでは `set -x`（xtrace）とエラートラップを組み合わせ、どのコマンドで失敗したかを必ずログに残す設計にする。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forwardエラーは「ローカルのHEADがリモートHEADの子孫でない」ときに発生する。自動化スクリプトで複数箇所からpushが走る場合、`commit → push` の後にリモートが先に進んでいると衝突する。正しい順序は必ず **`git pull --rebase → （ファイル変更） → git add → git commit → git push`**。
• `git pull --rebase` はローカルコミットを一時退避し、リモートの最新状態に乗せ直してから自分の変更を再適用するため、マージコミットを生まず履歴が線形に保たれる。ただし、すでにpush済みのコミットをrebaseすると他者の環境で履歴の乖離が起きるため、**shared branchでは使用禁止**。
• 自動化スクリプトでは `git config pull.rebase true` をあらかじめ設定しておき、pullを常にrebaseモードにする方法が推奨される。さらに `git stash` でコミット前の変更を一時退避してからpullし、その後unstashするパターンも衝突回避に有効。

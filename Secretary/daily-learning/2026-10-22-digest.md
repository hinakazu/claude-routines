**cronとPATH管理**
• cronはログインシェルを読まないため標準インストールパスしか持たない。スクリプト先頭で `export PATH=/usr/local/bin:/usr/bin:/bin:$HOME/.local/bin:$PATH` のように明示することで「手動では動くのにcronで動かない」を防げる。
• macOSではcronはlegacy扱いで、現代のmacOS（Sequoia以降）ではcronデーモンが実質動かないケースが報告されている。代替としてlaunchdのplistファイルで `EnvironmentVariables` キーを使いPATHを明示設定するのが公式推奨。
• 本番前テストは `env -i HOME=$HOME bash -c 'source ~/.bashrc && your_script.sh'` でcron相当の環境を模倣できる。ログ出力も `>> /path/to/cron.log 2>&1` で必ず残すこと。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` 単体には3つの主要な落とし穴がある：①コマンド置換 `$(...)` にはデフォルトで伝播しない（Bash 4.4以降は `shopt -s inherit_errexit` で対処可）、②`local var=$(cmd)` の形式はexitステータスをマスクする（`local var; var=$(cmd)` と分けること）、③`((count--))` が 0 を返すとexit status 1になりスクリプトが終了する。
• 推奨構成は `set -euo pipefail` ＋ `trap 'echo "ERROR: line $LINENO, exit $?" >&2' ERR` ＋ `trap cleanup EXIT` ＋ main関数でラップの4点セット。`pipefail` がないとパイプ前段の失敗が無音で通過する。
• ERR trap はサブシェルや関数内では伝播しない（`set -E`/`errtrace` で部分的に対処可）ため、デバッグ情報用に使い、クリーンアップは必ず `EXIT` trap に書くこと。

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトでgit操作を組み合わせる正しい順序は「fetch → 作業 → commit → push」。コミット前にpullしないと non-fast-forward で push が失敗し、pull → rebase すると今度は unstaged changes がある場合に rebase がブロックされる。`git config --global pull.rebase true` と `git config --global rebase.autoStash true` をセットにすることで、未コミット変更を自動stashして pull が通るようになる。
• 共有ブランチへの rebase は禁止。ローカルブランチ専用とし、push 時は `--force-with-lease` を使って他者の変更を誤って上書きしないようにする。
• `git rerere` を有効にすると（`git config --global rerere.enabled true`）、同じ衝突パターンの解消が自動的に記録・再適用されるため、長期間続く自動化ブランチでの繰り返し衝突を減らせる。

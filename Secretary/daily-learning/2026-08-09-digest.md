**cronとPATH管理**
• cronはユーザーの `.bashrc`/`.zshrc` を読み込まないため、対話シェルのPATHは無効になる。スクリプト冒頭に `export PATH=/usr/local/bin:/usr/bin:/bin:/opt/homebrew/bin` を明示することが最も確実な解決策。
• crontab先頭での `PATH=` 設定は全ジョブに効くが、`$PATH` の変数展開が効かないcron実装もあるため、絶対パスのみで書くのが安全。
• macOSのlaunchdを使う場合はplistの `EnvironmentVariables` セクションでPATHを指定する。Apple Silicon Macは `/opt/homebrew/bin` を必ず含める。
• プロダクション環境ではラッパースクリプトで環境をセットアップしてから本体を呼ぶ方式が最もテスタブルで自己文書化しやすい。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は `&&`/`||` リストの途中コマンド、`if`/`while` の条件部、コマンド置換内では発動しない。また `(( i++ ))` がゼロ評価されただけでスクリプトが終了するという罠もある。
• `trap 'handle_error "$?" "$BASH_COMMAND"' ERR` を使うと、エラー発生時のコマンド名と終了コードをキャプチャしてログに残せる。`-E`（errtrace）を併用すると関数・サブシェルにもトラップが継承される。
• `set -e` は安全ネットとして使いつつ、ERRトラップで確実にログを取る設計が堅牢。ShellCheckでスクリプトを静的解析すると未検出の罠を事前に発見できる。

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトで複数箇所からpushが発生するリポジトリでは `git stash → git pull --rebase → git stash pop → git commit → git push` の順序が必須。commitの前にpullしないとnon-fast-forwardエラーが発生する。
• Git 2.6以降は `git rebase --autostash`（または `git pull --rebase --autostash`）が使え、pull前の自動stash・後の自動適用を1コマンドで処理できる。
• stashには `git stash push -m "WIP: 説明"` で説明をつけておくと、pop失敗時の原因追跡が容易になる（2025年ベストプラクティス）。

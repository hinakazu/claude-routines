**cronとPATH管理**
• cronジョブはユーザーシェル（.zshrc等）を読み込まないため、デフォルトPATHは `/usr/bin:/bin` のみ。スクリプト冒頭か crontab の先頭で `PATH=/usr/local/bin:/usr/bin:/bin:...` を明示するか、すべてのコマンドを絶対パスで書くことが必須。
• `$PATH` を crontab 内で展開しようとしても多くの実装では変数展開されず文字列 "$PATH" になるため、必ずフルパスを直書きする。`SHELL=/bin/bash` も明示しないと sh として実行される。
• macOS では Apple が推奨する **launchd**（LaunchAgent）への移行が長期的な解決策。launchd はスリープ復帰後も実行され、GUIセッションへのアクセスやイベント起動も可能。cron は今も動くが PATH 問題を含む制限が残る。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は条件式（`if`）・`||`/`&&` チェーン・サブシェル内では発火しない落とし穴がある。`true && fail_cmd` はexit 0 扱い、`fail_cmd && true` は終了する、という非直感的な挙動が混乱を生む。
• ベストプラクティスは **`set -euo pipefail`** ＋ **`trap 'echo "ERROR: line $LINENO, exit $?" >&2' ERR`** の組み合わせ。`set -E`（errtrace）を追加するとシェル関数・コマンド置換・サブシェルにも ERR トラップが継承される。
• `trap cleanup EXIT` でスクリプト終了時（正常・異常問わず）に一時ファイル削除やプロセス終了を行うクリーンアップ関数を登録するのがプロダクション品質の定番パターン。cronでは終了コード `$?` を必ずログに記録することで無音失敗を可視化できる。

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトでの正しい git 操作順序は `git pull --rebase → ファイル配置 → git add → git commit → git push`。未コミット変更がある状態で `pull --rebase` を実行すると "cannot rebase: you have unstaged changes" でブロックされ、それが無音で終了するとpushまで到達しない。
• `git pull --rebase` はリモートの最新コミットを取得し、ローカルコミットをその上に replay して履歴を線形に保つ。一方でリモートにpush済みのコミットを rebase すると他者の作業を破壊するため、自動化では**ローカルのみで行う**ことが大原則。
• 複数箇所からpushが発生するリポジトリでは `git config pull.rebase true` を設定してデフォルトをrebase戦略にするか、pushごとに `--force-with-lease`（force-pushより安全）を使って意図しない上書きを防ぐ。

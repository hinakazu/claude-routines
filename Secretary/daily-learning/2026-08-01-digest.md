**cronとPATH管理**
• cron は `~/.zshrc` や `~/.bash_profile` を読み込まないため、PATH は `/usr/bin:/bin:/usr/sbin:/sbin` 程度の最小構成になる。Homebrewや `/Applications/*.app/Contents/Resources/bin` にあるツールは見つからずexit 127でサイレント失敗する。
• 対策は3択：①スクリプト冒頭で `PATH=...` を明示的に設定する、②コマンドをすべて絶対パスで記述する、③cronの代わりにlaunchdを使う（macOS推奨）。
• macOS では launchd が公式後継。launchd の plist ファイルで `EnvironmentVariables` キーを使えば、ジョブごとにPATHを宣言的に設定できる。またスリープ中に発火時刻を過ぎても起動後に遅延実行してくれるため、cronより信頼性が高い。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は「コマンド失敗で即終了」だが、①`if`/`||`/`&&` 内のコマンド、②`local var=$(cmd)` の代入（`local` のexit codeが0になり失敗を隠蔽）、③サブシェルでは発火しないという重大な例外がある。
• 推奨の組み合わせは `set -euo pipefail`。`-u` で未定義変数をエラーに、`-o pipefail` でパイプ途中の失敗も検知できる。さらに `trap 'echo "Error at line $LINENO: $BASH_COMMAND" >> error.log' ERR` を加えると、失敗したコマンドと行番号をログに記録できる。
• Bashの有識者の間では「set -e だけに頼るな」が定説。代わりに `cmd1 && cmd2 && cmd3` で明示的にチェーンするか、各コマンド直後に `|| { echo "失敗: $?"; exit 1; }` でexit codeを明示的にキャッチする設計が推奨されている。

**git non-fast-forward push と自動化スクリプトの操作順序**
• 自動化スクリプトでの正しいgit操作順序は「**pull → ファイル書き込み → add → commit → push**」。`cp → commit → pull → push` という順序ミスが、unstaged changes で rebase をブロックする原因になる。
• 複数の書き込み元（cronジョブ + 手動操作など）が同一リモートブランチに書く場合、commitとpushの間に他のpushが入るレースコンディションが発生しうる。push失敗時は `git pull --rebase && git push` を自動リトライする設計で対処する。
• `git pull --rebase` を使うと履歴が線形に保たれる。`--force` は避け、`--force-with-lease` を使えばリモートに予期せぬコミットがある場合に上書きを防げる。

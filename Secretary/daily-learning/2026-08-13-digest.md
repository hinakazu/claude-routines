**cronとPATH管理**
• cronジョブはユーザーの `.zshrc` / `.zprofile` を読み込まず、PATHは `/usr/bin:/bin` のみ。macOSのlaunchdも同様で `HOME`、`USER`、`TMPDIR` 以外ほぼ空の環境で起動するため、スクリプトが手動では動くのにcronでは動かない典型的な罠となる
• 対策は3層構造：①スクリプト冒頭で `PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin` を明示設定、②crontabファイルの先頭行に `PATH=...` を記述、③コマンドは絶対パスで指定（最終フォールバック）
• launchdの場合はplistの `<key>EnvironmentVariables</key>` でPATHを設定するのが公式推奨。`.zshenv` は非ログイン非インタラクティブシェルでも読まれるため、そこにexportするのも有効な補完策

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は条件式・`||/&&` チェーン・サブシェル内では無効化されるため、意図せず失敗が素通りする落とし穴がある。`set -euo pipefail` にして未定義変数検知とpipeのエラー伝播も追加するのが本番スクリプトの最低ライン
• `trap 'echo >&2 "Error on line $LINENO: $BASH_COMMAND"; exit $?' ERR` を組み合わせると `set -e` が到達しないコンテキストでもエラーをキャッチできる。エラー報告（ERR trap）と後処理（EXIT trap）を分離する2段構成がプロダクションテンプレートとして確立されている
• サブシェル `$(...)` の中で `set -e` の関数を呼ぶと親プロセスが気づかずに処理を続けるため、重要な戻り値は変数に受けて `[ -n "$result" ] || exit 1` のように明示チェックが必須

**git自動化スクリプトの操作順序とunstaged changes対策**
• non-fast-forward エラーは「ローカルにないリモートコミットが存在する状態でpushしようとした」ときに発生。自動化スクリプトでは複数プロセスが同一ブランチにpushする構成そのものを避け、専用ブランチ運用を基本とする
• unstaged changes がある状態で `git pull --rebase` を実行するとリベースがブロックされる。`git pull --rebase --autostash` でリベース前に自動stash・復元するか、スクリプト内で `git stash` → `pull --rebase` → `git stash pop` の3ステップを明示的に踏む。正しい操作順序は「pull → 変更 → commit → push」
• `git config --global pull.rebase true` と `git config --global rerere.enabled true`（過去の競合解決を記憶して自動適用）をリポジトリのセットアップに含めておくと、自動化スクリプト全体の競合耐性が上がる

**cronとPATH管理**
• cronジョブはデフォルトで `PATH=/usr/bin:/bin` のみの最小環境で動作し、`.zshrc` や `.bashrc` は一切読み込まれない。`/opt/homebrew/bin` や独自インストールのバイナリが見つからず exit 127 でサイレント終了するのが典型的な罠。
• 対策は3つの層を組み合わせる：① crontab先頭に `SHELL=/bin/bash` と `PATH=/usr/local/bin:/usr/bin:/bin:/opt/homebrew/bin` を明示 ② スクリプト内でも `export PATH=...` を宣言 ③ コマンドは絶対パスで記述。変数展開（`PATH=$PATH:...`）はcron実装によって動作しないため必ず全記述する。
• macOS では launchd が推奨。cron はスリープ中に実行をスキップするが launchd は次回起動時にリトライできる。launchd では `~` が展開されないため plist の全パスに `/Users/yourname/` を明示する必要がある。デバッグ時は `env -i /bin/bash script.sh` でcron環境を手元で再現できる。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` だけでは不十分で、3つをセットで使うのが現代のベストプラクティス：`set -euo pipefail`。`-u` は未定義変数を検出（`rm -rf /$undefined_var` 系の事故を防ぐ）、`-o pipefail` はパイプ内の途中失敗を捕捉する。この3つが揃って初めて「サイレント失敗しないスクリプト」になる。
• `set -e` が発動しない例外ケースを把握することが重要：`if/while/until` の条件節、`&&`/`||` チェーン内、サブシェル内では非ゼロ終了でもexitしない。また `((count++))` は初回ループで 0（失敗扱い）を返して即終了する罠がある。
• `trap ERR` でエラー発生時の集中処理（ログ書き込み・クリーンアップ）を実装し、`trap EXIT` でスクリプト正常終了・異常終了問わずリソース解放を行うパターンが信頼性を高める。GitHubユーザー調査では `trap "cleanup" EXIT` 採用後にリソースリークが40%減少したとの報告がある。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forward エラーはリモートが自分のローカルより先にコミットがある状態でpushしようとしたときに発生する。自動化スクリプトで複数箇所から同一リポジトリに書き込む場合は必ずこの状況が生じる。正しい解消手順は `git pull --rebase origin <branch>` → コンフリクト解消 → `git push` の順。
• 自動化スクリプトの安全な git操作順序は「pull → 変更 → commit → push」。変更後にpullすると unstaged changes で rebase がブロックされる。スクリプトでは `git fetch && git stash && git rebase origin/main && git stash pop` のようにstashを挟んで状態を安全に保つ手法も有効。
• 強制pushが必要な場合は `--force` ではなく `--force-with-lease` を使う。`--force` はリモートの状態を無視して上書きするが `--force-with-lease` はリモートが想定外の状態なら失敗してくれるため、他者のコミットを消す事故を防げる。pre-push フックに `git fetch && git rebase` を仕込む方法も自動化に有効。

**cronとPATH管理**
• cronのデフォルトPATHは `/usr/bin:/bin` のみ。`/usr/local/bin` や `~/.zshrc` で追加したパスは反映されない。crontabの先頭で `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin` と明示的に宣言する方法が最も確実。
• macOSでは cron よりも launchd が推奨。launchd の `.plist` ファイルで `EnvironmentVariables` を指定してPATHを設定できる。Sequoia以降ではcronデーモンが事実上機能しないケースも報告されている。
• 本番投入前の検証は `env -i HOME=$HOME /bin/sh -c "your_script.sh"` でcron環境を再現できる。絶対パス指定も防御的手段として有効。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` 単独では失敗ログが残らない。`trap 'echo "Error at line $LINENO"' ERR` と組み合わせることで障害箇所を特定できる。`set -euo pipefail` のセットで記述するのがベストプラクティス。
• `set -e` の落とし穴：`local var=$(cmd)` はコマンド失敗でも exit 0 を返すため `set -e` が発動しない。`((count--))` がゼロに達したとき非ゼロを返しスクリプトが意図せず終了する。これらは `|| true` で対処する。
• cronジョブでは標準エラーもログにリダイレクト（`>> /var/log/script.log 2>&1`）し、スクリプト内にタイムスタンプを出力する設計が必須。`set -x` + カスタム `PS4` でトレースすると失敗箇所の特定が高速化する。

**git non-fast-forward と自動化スクリプトの操作順序**
• 自動化スクリプトでの安全な操作順序：`git fetch → git pull --rebase --autostash → ファイル操作 → git add → git commit → git push`。ファイルコピーをpullより前に実行すると unstaged changes が rebase をブロックするため必ずpull後に実施する。
• `git pull --rebase --autostash` を使うとローカルの未コミット変更をスタッシュに退避してからリベースするため、自動化フローでの衝突リスクを低減できる。共有ブランチへの rebase は履歴書き換えになるため注意。
• force push が必要な個人ブランチでも `--force-with-lease` を使う。これはリモートのHEADが想定外に変わっていた場合に失敗させる安全策で、他者の変更の上書き事故を防ぐ。

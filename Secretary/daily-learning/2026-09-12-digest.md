**cronとPATH管理（cron・launchd）**
• cronジョブはユーザーの `.zshrc` や `.bashrc` を読み込まない。デフォルトのPATHは `/usr/bin:/bin` だけで、Homebrew・NVM等のカスタムパスは全て未登録になる。最も確実な対策は、crontab冒頭で `PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin` のように宣言するか、スクリプト内で絶対パスを使うこと。
• デバッグ時は一時的に `* * * * * env > /tmp/cron-env-$(date +\%H\%M).txt` をcronに仕込んで、cronが実際に受け取っている環境変数をダンプする方法が有効。
• macOSではAppleがcronを非推奨とし、launchdへの移行を推奨。launchdもデフォルトのPATHは最小限だが、plistの `EnvironmentVariables` キーで明示設定でき、スリープ後の実行再開・ファイル変更トリガー等の機能もある。Apple Siliconでは `/opt/homebrew/bin` を必ず追加すること。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は条件文（if/||/&&）やサブシェル内では効かない。パイプラインもデフォルトでは最後のコマンドの終了コードしか見ないため途中の失敗を検出できない。対策は `set -euo pipefail` をセットで使うこと（`-u` は未定義変数を検出、`pipefail` はパイプの中間失敗を検出）。
• `trap 'echo "エラー: line $LINENO, exit=$?" >&2' ERR` を使うと、エラー発生時に行番号付きのログを出力できる。関数やサブシェルにも継承させるには `-E`（errtrace）フラグが必要で、`set -Eeuo pipefail` が堅牢な自動化スクリプトの定石。
• 特定コマンドだけエラーを無視したい場合は `command || true` パターンを使う。終了コードを変数にキャプチャして後続処理で判断する設計（`cmd; rc=$?; if [ $rc -ne 0 ]; then log_error; fi`）が保守性が高い。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forwardエラーはローカルとリモートの履歴が分岐したとき発生する。自動化スクリプトでの正しい操作順序は「fetch → stash（未コミット変更がある場合）→ pull --rebase → stash pop → add → commit → push」。未コミット変更がある状態で `git pull --rebase` を実行するとリベースがブロックされる。
• 自動化では `git stash -u`（未追跡ファイルも含む）で退避してから pull し、処理後に `git stash pop` するパターンが安全。失敗時もstashに退避されているので作業を失わない。
• 複数箇所（cronジョブ＋手動等）から同一リポジトリにpushする構成では、`git config pull.rebase true` をグローバル設定してマージコミットを作らない運用が推奨。さらに `git config rebase.autoStash true` を設定すると、未コミット変更がある状態でのrebaseを自動的にstash/unstashしてくれる。

**cronとPATH管理**
• cronジョブ実行時のPATHは最小限（`/usr/bin:/bin` のみ）で、ユーザーの `.zshrc`/`.bash_profile` は一切読み込まれない。`/Applications/cmux.app/.../bin` のようなカスタムパスは crontab 先頭に `PATH=/usr/local/bin:/usr/bin:/bin:/your/custom/path` と完全パスで明示する必要がある。
• `PATH=$PATH:/追加パス` 形式は一部のcron実装で変数展開が効かないため使用禁止。すべてのパスをフルパスで列挙するか、環境設定専用のラッパースクリプト経由にするのが安全。
• macOSではcronより **launchd** が推奨。launchd の `EnvironmentVariables` でPATHを宣言すればジョブごとに独立した環境を持てる。スリープ中にcronがジョブをスキップする問題も launchd では wake 後のリカバリで回避できる。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` 単独には重大な落とし穴がある：`if` / `||` / `&&` 構文やサブシェル内ではエラーを無視し、`(( i++ ))` のように結果が0になる算術演算でも即終了してしまう。
• 推奨パターンは **`set -euo pipefail`** の3点セット。`-u` で未定義変数をエラーにし、`-o pipefail` でパイプライン途中の失敗を検知。加えて `trap 'echo "Error at line $LINENO: $BASH_COMMAND (exit $?)" >&2' ERR` を設定するとサイレント終了を防止できる。
• ERR トラップを関数・サブシェルにも継承させるには `set -E`（errtrace）が必要。終了時クリーンアップには `trap cleanup EXIT` を別途設定するのが定石。特定コマンドだけエラーを無視したい場合は `command || true` を使う。

**git non-fast-forward push と自動化スクリプトでの操作順序**
• non-fast-forward エラーはローカルとリモートが分岐した状態でpushするときに発生。自動化スクリプトでは「変更 → commit → pull → push」という誤った順序が原因になりやすく、正しくは **「pull → 変更 → add → commit → push」**。
• `git pull --rebase` を使うとリモートの変更を取り込んだ上にローカルコミットを積み直すため、マージコミットを作らずクリーンに解消できる。ただし push 前に unstaged changes があると rebase がブロックされるため、必ず add/commit または `git stash` してから pull する。
• 自動化の文脈では push 失敗時に pull してリトライするべき等な仕組みが必要。GitHub の `git-auto-commit-action` でも同様の問題が Issue で報告されており、マルチ環境からの自動pushには競合対策が必須。

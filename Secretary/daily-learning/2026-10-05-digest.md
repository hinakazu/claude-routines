**cronとPATH管理**
• cronは `/usr/bin:/bin` のみの最小限PATHで動作し、ユーザーの `.zshrc`/`.bashrc` は一切読み込まれない。`claude` や `node`、Homebrew製コマンドが exit 127 でサイレント失敗する典型的な原因。
• crontab冒頭に `PATH=/usr/local/bin:/usr/bin:/bin:/opt/homebrew/bin` を明示指定するか、コマンドの絶対パスを使うのが基本対策。変数展開（`PATH=$HOME/bin:$PATH`）は cron 内では機能しないので注意。
• macOS では cron は2005年から非推奨。launchd に移行すると、ジョブごとに `EnvironmentVariables` を宣言的に設定でき、スリープ復帰後の実行漏れも防げる。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` 単体では関数・サブシェル・コマンド置換の中で ERR トラップが継承されない。`-E`（errtrace）フラグを追加することで、関数内の失敗にもトラップを伝播できる。
• 本番スクリプトの推奨パターンは `set -Eeuo pipefail` + `trap 'handler $LINENO "$BASH_COMMAND" $?' ERR`。`$LINENO` と `$BASH_COMMAND` を活用すると「何行目のどのコマンドが失敗したか」が即座にわかる。
• `(( i++ ))` のような算術式は値が 0 のとき非ゼロ終了コードを返すため `set -e` が誤発動する。`(( i++ )) || true` か `i=$(( i + 1 ))` で回避する。

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトでの安全な操作順序は `git stash push -u` → `git pull --rebase` → `git stash pop` → `git add` → `git commit` → `git push`。コピー操作を pull より先に行うと unstaged changes で rebase がブロックされる。
• `git config rebase.autostash true` を設定しておくと `git pull --rebase` が自動で stash/pop を行うため、スクリプトを簡略化できる（ただし競合時は手動対応が必要）。
• 共有ブランチへの force-push は `--force-with-lease` を使うことで他者の新規コミットを上書きするリスクを軽減できる。

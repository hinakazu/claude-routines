**cronとPATH管理**
• cronジョブではユーザーの `.zshrc` / `.bash_profile` が読み込まれないため、`/usr/local/bin` や `/opt/homebrew/bin` などがPATHに含まれず `exit 127` でサイレント失敗する。macOSのlaunchdでは `/usr/bin:/bin:/usr/sbin:/sbin` のみが初期PATHとなる。
• 最も安全な対策はスクリプト冒頭に `PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin` を明示的に記述すること。代替策として `sudo launchctl config system path '...'` でシステムレベルのPATHを変更する方法もあるが再起動が必要。
• ラッパースクリプト方式（環境設定を担うスクリプトが実際のジョブを呼び出す構造）は、テスト・文書化の観点でも優れた設計パターン。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` 単体では、条件式・`||`/`&&` チェイン・サブシェル内でエラーが起きても終了しないケースがある。`set -Eeuo pipefail`（`-E` でERRトラップをサブシェル・関数に継承）をスクリプト先頭行に置くのが2025年の推奨スタイル。
• `trap 'handle_error $LINENO "$BASH_COMMAND" $?' ERR` を定義すると、失敗コマンド名・行番号・終了コードをすべてログに残せる。`set -x` と組み合わせると実行トレースも出力されデバッグが大幅に楽になる。
• `trap cleanup EXIT` でEXIT時クリーンアップ（一時ファイル削除・バックグラウンドプロセス停止）を保証すると、エラー時・正常終了時の両方で安全にリソース解放できる。

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトで `cp → commit → pull --rebase → push` の順だと「unstaged changes があるため rebase できない」エラーが出る。正しい順序は `pull → ファイル変更 → commit → push`。
• Git 2.7以降では `git config --global rebase.autostash true` を設定すると、`git pull --rebase` 実行時にunstaged changesを自動stash→rebase→stash popしてくれる。自動化スクリプトへの組み込みに最適。
• stash popでコンフリクトが起きるケースに備え、スクリプトでは `git stash push -m "WIP: before pull" && git pull && git stash pop` の三段階方式も堅牢な選択肢。

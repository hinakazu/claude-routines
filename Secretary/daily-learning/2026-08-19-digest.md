**cronとPATH管理**
• cronは起動時に最小限の環境しか持たない（`PATH=/usr/bin:/bin` のみ）。`.zshrc` や `.bashrc` は一切読まれないため、Homebrew・nvm・pyenv経由のコマンドは`exit 127`でサイレント失敗する。
• 解決策は3層: ①crontabの先頭に `SHELL=/bin/bash` と `PATH=...` を明示 ②ラッパースクリプト内でPATHを設定してから本体を呼ぶ ③コマンドに絶対パスを使う。デバッグは `env > /tmp/cron-env.txt` をcronで実行して実環境を確認するのが最速。
• macOSでは Apple がcronを非推奨にしてlaunchdを推奨。ただしlaunchdも最小PATHで起動するため、plistの `EnvironmentVariables` に `/opt/homebrew/bin` を追加することが必須（Apple Siliconでは特に忘れやすい）。sleep中はcronがジョブをスキップするが、launchdは起床後に実行を試みる点も重要な差異。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は一見安全に見えるが「if文の条件式」「`||`/`&&` チェーン」「サブシェル」内では機能しない。さらに `(( i++ ))` が0を返す場合にも即終了するという落とし穴がある。ログなしで終了するため原因特定が困難。
• 推奨パターンは `set -euo pipefail` をスクリプト先頭に置くこと。`-u` は未定義変数を即エラーに、`-o pipefail` はパイプ途中の失敗を伝播させる。2023年ShellCheckユーザー調査でこのパターンを使っていないスクリプトの60%以上でサイレントなデータ損失が発生していた。
• `trap 'error_handler $LINENO "$BASH_COMMAND" $?' ERR` を組み合わせると、`set -e` がスキップする条件式内でも全エラーをキャッチできる。`trap cleanup EXIT` でクリーンアップも必ず実行されることを保証する。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forwardエラーはローカルとリモートの両方に独立したコミットがあり「diverged」状態になっているときに発生。自動化スクリプトでは `commit → pull → push` の順序が誘発しやすい典型的な罠。
• 正しい操作順序は `pull --rebase → (変更を加える) → commit → push`。`git pull --rebase` はリモートの変更を取り込んだうえでローカルのコミットをその上に積み直すため、マージコミットなしにクリーンな履歴を維持できる。
• 自動化環境（Dependabot・release-please・Claude Routineなど複数ボットが同時にpushする状況）では、push直前に `git pull --rebase` を再実行するリトライロジックを入れることが実務上の必須対策。ファイル変更が1件のみのボットコミットは通常rebaseで自動解決される。

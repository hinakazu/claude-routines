**cronとPATH管理**
• cronはユーザーの`.bashrc`/`.zshrc`を読み込まず、デフォルトPATHは`/usr/bin:/bin`のみ。スクリプト内か`crontab -e`の冒頭で`PATH=/usr/local/bin:/usr/bin:/bin:...`を明示指定するか、コマンドに絶対パスを使うのが基本。
• macOSではAppleがlaunchdを推奨。plistの`<key>EnvironmentVariables</key>`内でPATHを設定し、Apple Siliconなら`/opt/homebrew/bin`も必須。`~`は展開されないので絶対パスのみ使用。
• launchdはスリープ中に実行されなかったジョブをOS再起動・スリープ解除後に自動的に遅延実行できる（cronはスキップするだけ）。この差が自動化の信頼性に直結する。

**bash `set -e` のサイレント終了とエラーハンドリング設計**
• `set -e`は`if`文・`&&`/`||`チェーン・サブシェル内では自動的に無効になる落とし穴がある。`set -E`（errtrace）と組み合わせることで、関数・サブシェル内でも`trap ERR`が継承される。
• ベストプラクティスは`set -Eeuo pipefail`を冒頭に置き、`trap 'echo "ERR at line $LINENO, cmd: $BASH_COMMAND" >&2' ERR`でエラー発生行番号とコマンドをログに残す。`pipefail`がないとパイプラインの途中失敗を見逃す。
• `set -u`で未定義変数アクセスを即エラー化し、デフォルト値が必要な場合は`${VAR:-default}`で安全に扱う。この4オプション組み合わせでサイレント失敗をほぼ根絶できる。

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトでのgit操作の正しい順序は「`git pull --rebase` → ファイル変更・コピー → `git add` → `git commit` → `git push`」。`cp`などのファイル変更をpullより前に行うとunstaged changesがrebaseをブロックする。
• push失敗（non-fast-forward）時には自動リトライロジック（pull→push再試行）を組み込むことで自動化スクリプトの堅牢性が増す。共有ブランチへのrebaseは禁止（ローカルのみ）で、共有ブランチはmerge commitを使う。
• `git fetch origin <branch>` → `git rebase origin/<branch>` の分割コマンドにすると、stash不要でuncommitted changesがある場合も安全にbase更新できる。

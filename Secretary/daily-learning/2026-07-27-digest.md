**cronとPATH管理**
• cronジョブはユーザーの `.zshrc` / `.bashrc` を一切読み込まないため、デフォルトのPATHは `/usr/bin:/bin` のみ。`/usr/local/bin` や `/opt/homebrew/bin` は含まれず、`claude` や `node` などのコマンドがexit 127でサイレント失敗する
• 最も確実な対策はcrontabの先頭行に `PATH=/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin:/opt/homebrew/bin` を明記すること。またはスクリプト内で絶対パスを使う
• デバッグは `* * * * * env > /tmp/cron-env-$(date +\%H\%M).txt` を仕込んで実際のcron環境変数を書き出すと原因特定が速い
• macOS 2025では Apple が launchd への移行を推奨。launchd は各ジョブごとに独立した `EnvironmentVariables` を設定でき、Apple Silicon Mac では `/opt/homebrew/bin` を忘れず追加。さらにスリープ中に missed した実行を復帰後に自動補完する機能があり、cronより信頼性が高い

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は `&&` / `||` / `if` の条件部・`while`/`until` 条件・`!` 反転の中ではfalseでも終了しない。また `(( i++ ))` がゼロを返すと無条件終了するので `(( i++ )) || true` か `i=$(( i + 1 ))` を使う
• ERR トラップを関数やサブシェル内でも継承させるには `set -E`（errtrace）が必須。推奨セットは `set -Eeuo pipefail`
• `trap 'echo "FAIL: line $LINENO in ${FUNCNAME[0]:-main}" >&2' ERR` のようにハンドラーを設定すると、失敗箇所のファイル・関数名・行番号をログに残せる。`set -e` だけでは「死んだ」事実しか分からない
• ShellCheck を CI に組み込むと `set -e` の落とし穴（pipefail 忘れ、unquoted 変数など）を静的解析で事前検出できる

**git non-fast-forward push と rebase の操作順序**
• non-fast-forward は「リモートにあるコミットがローカルに存在しない状態でpushしようとした」ときに発生。自動化スクリプトで `cp → commit → pull → push` の順だと unstaged changes が rebase をブロックしてさらに詰む
• 正しい操作順序は `git fetch → git stash（未コミット変更があれば）→ git rebase origin/main → stash pop → cp / 変更 → git add → git commit → git push`。または `git pull --rebase origin branch` で fetch + rebase を一発で実行
• 共有ブランチ（main / master）への rebase は他メンバーのコミット履歴を書き換えるため禁止。rebase はローカルのfeatureブランチ限定のルールを自動化スクリプトのコメントに明記しておく
• CI/CD パイプラインでは rebase 後に自動テストをトリガーする構成が2025年の標準。clean commit history を維持することでデバッグ・bisect の効率が上がる

**cronとPATH管理**
• cronはユーザーの `.zshrc` / `.bash_profile` を読み込まず、PATH は `/usr/bin:/bin` 程度しかない。`nvm`・`pyenv`・`asdf` などバージョンマネージャのshimも全滅する。スクリプト冒頭で `PATH=/usr/local/bin:/usr/bin:/bin:$HOME/.local/bin` のように明示するか、コマンドを絶対パスで書くのが基本。
• macOS では Apple が cron を launchd に吸収しており、Sequoia以降では crond がそもそも起動しないという報告もある（個人ブログ情報、要確認）。定期ジョブを本番運用するなら launchd の `.plist` + `EnvironmentVariables` で明示指定する方が安全。
• cron環境のシミュレーションは `env -i HOME=$HOME /bin/sh your_script.sh` で可能。実行前に必ずこの方法でテストすると「手動OK・cron NG」のトラブルを事前につぶせる。出力は `>> /var/log/job.log 2>&1` で必ずstderrも記録する。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` には多数の例外がある。`if`・`&&`・`||` の中のコマンド失敗ではトリガーされず、パイプライン途中の失敗も末尾コマンドが成功なら無視される（`pipefail` 未設定の場合）。「安全策」として使っていても実は穴だらけ。
• コマンド置換 `$(...)` 内の失敗はデフォルトで `set -e` をトリガーしない（Bash 4.4以降は `set -o inherit_errexit` で対処可能）。`local var=$(failing_cmd)` のように `local` と組み合わせると終了ステータスが `local` の成功で上書きされて失敗が無視される典型的なバグになる。
• 推奨パターンは `set -euo pipefail` + `trap 'echo "ERR at line $LINENO, exit $?" >&2' ERR` + `trap cleanup EXIT` の組み合わせ。ERR トラップはサブシェルには継承されないため `set -E`（errtrace）も合わせて設定する。エラー時に行番号と終了コードをログに残すことでサイレント失敗を防ぐ。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forward エラーの根本原因は「リモートにローカルが持っていないコミットが存在する状態でpushしようとする」こと。自動化スクリプトで複数環境から同じリポジトリにpushすると必ず発生する。
• 正しい操作順序は `git fetch origin` → `git pull --rebase` → 変更を加える → `git commit` → `git push`。変更を加えてからpullするとunstaged changesのせいでrebaseがブロックされる。`--autostash` オプションを使うとコミット前の変更を自動でstash/unstashしてくれるので自動化スクリプトには `git pull --rebase --autostash` が便利。
• `git config --global pull.rebase true` でデフォルト動作をrebaseに固定すると全マシンで統一できる。自動化スクリプトでは `--force-with-lease`（他人のコミットが存在する場合は失敗する安全なforce push）以外の force push は絶対避ける。重要なrebaseの前にはバックアップブランチを作成してから実施する。

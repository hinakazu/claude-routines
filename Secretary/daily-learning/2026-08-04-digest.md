**cronとPATH管理（macOS自動化の典型的な罠）**
• cronはユーザーの `.zshrc` や `.bashrc` を読み込まないため、Homebrew(`/opt/homebrew/bin`)やアプリ独自バイナリが見つからずexit 127でサイレント失敗する。対策①: crontabの先頭行に `PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin` を明示。対策②: スクリプト冒頭でも `export PATH=...` を再定義する二重防衛が安全。
• macOSでは `launchd` がApple公式の推奨代替手段。cronはスリープ中のジョブをスキップするが、launchdはウェイク後に補完実行できる。plistの `EnvironmentVariables` キーにPATHを書く方式でcronと同様の問題を回避できる。
• デバッグ法: crontabに `env > /tmp/cron-env.txt` を一時追加し、通常シェルの `env > /tmp/shell-env.txt` と `diff` で比較すると欠けているパスがすぐ判明する。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e`（errexit）は一見安全だが「条件式・ループ条件・パイプ途中・`&&`/`||`の途中コマンド」では発動しない。例: `if some_cmd; then ...` の `some_cmd` が失敗してもスクリプトは終了しない。
• 安全な組み合わせは `set -eE -o pipefail -o inherit_errexit` + `trap 'handle_error "$?" "${BASH_COMMAND}"' ERR`。`-E`（errtrace）を付けないと関数・サブシェル内のエラーがトラップされず、サイレント失敗の原因になる。
• 推奨パターン: エラーハンドラ関数でコマンド名と終了コードをstderrに出力→必ずログに残す。`trap cleanup EXIT` を組み合わせてリソースリークも防ぐ。このパターン採用後にリソースリーク40%減という報告あり。

**git non-fast-forward push と自動化スクリプトの操作順序**
• non-fast-forwardエラーはリモートブランチがローカルの親コミットでない状態でpushしたときに発生。正しい操作順序は `git pull --rebase` → ファイル生成/修正 → `git add` → `git commit` → `git push`。「ファイルをコピーした後にpull」の順序が最も踏みやすいミス。
• `git pull --rebase` が推奨される理由: マージコミットを作らずリニアなhistoryを保てるうえ、ローカルコミットをリモートの先頭に積み直せる。グローバル設定 `git config --global pull.rebase true` で常にrebase動作にできる。
• 自動化スクリプトで競合が起きた場合の安全なパターン: `git stash → git pull --rebase → git stash pop → git add → git commit → git push` の順で吸収する。

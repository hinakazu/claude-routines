**cronとPATH管理**
• cronジョブでは `.zshrc`/`.bashrc` が読み込まれず最小限のPATHしか設定されない。`/Applications/cmux.app/...` 等のカスタムパスが未登録で `exit 127` サイレント失敗が起きる典型パターン
• 対策①：スクリプト冒頭で `export PATH=/usr/local/bin:/usr/bin:/bin:/your/custom/path:$PATH` を明示的に宣言する
• 対策②：crontab の先頭行に `PATH=...` を記述（ただし `$HOME/bin:$PATH` のような変数展開は不可）
• デバッグ法：`* * * * * env > /tmp/cron_env.txt` で cron 実行時の実際の環境変数を書き出して確認
• macOSでは Apple が `launchd` を正式推奨。`.plist` の `EnvironmentVariables` キーで PATH を設定し、スリープ後の取りこぼしも防げる

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は「失敗で即終了」だがパイプ途中のエラーは素通り → `set -o pipefail` を必ず併用すること
• `$(コマンド置換)` 内のエラーは `set -e` で伝播しない：`result=$(failing_cmd)` が失敗してもスクリプトは続行してしまう罠
• `((count--))` の結果が 0 になると終了コード 1 → 意図せず `set -e` でスクリプトが止まる落とし穴（対策は `|| true` を付ける）
• 推奨パターン：`set -euo pipefail` + `trap 'echo "Error at line $LINENO"' ERR` + `trap cleanup EXIT`
• `set -E`（大文字）を追加するとサブシェル・関数にも ERR トラップが継承される

**git non-fast-forward push と rebase の操作順序**
• non-fast-forward とは：リモートに自分が持っていないコミットがある状態で push すると1本の履歴線にならずリジェクトされる現象
• 自動化スクリプトで頻発するミス：「ファイルをコピー → commit → pull → push」の順序。pull 時に unstaged changes が残っていると rebase がブロックされる
• 正しい順序：`git fetch` → `git pull --rebase` → ファイル変更 → `git add` → `git commit` → `git push`
• `git config pull.rebase true` でデフォルト挙動を rebase に固定しておくと自動化スクリプトで安全
• 防御策：`git status --porcelain` で作業ツリーがクリーンか確認してから pull/rebase を実行する

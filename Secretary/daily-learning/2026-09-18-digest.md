**cronとPATH管理**
• cronは起動時に `PATH=/usr/bin:/bin` のみ設定され、`.zshrc` や `.bash_profile` は一切読み込まれない。`/opt/homebrew/bin` 等のカスタムパスはすべて未登録になる。
• crontabの先頭行で `PATH=/usr/local/bin:/usr/bin:/bin:/opt/homebrew/bin` のように明示定義するか、スクリプト内でバイナリの絶対パスを使うのが鉄則。
• デバッグ時は `* * * * * env > /tmp/cron-env.txt` を一時追加することで、cronが実際に受け取っている環境変数を丸ごと確認できる。
• macOS環境ではAppleが推奨するlaunchdへ移行すると、plistファイル内でジョブごとに環境変数を宣言できるためPATH問題を根本的に回避できる。cronではスリープ中のジョブがスキップされるが、launchdは起動後に追いつき実行する点も優秀。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は条件式 `if`・論理演算子 `||/&&` の右辺・サブシェル `$()` 内では発動しないため、「エラーなのにスクリプトが続行する」または「意図せず終了する」という挙動が起きる。
• 推奨パターンは `set -euo pipefail`。`-u` は未定義変数を検知し、`-o pipefail` はパイプ途中の失敗を検知する。この3つセットで主要なバグの90%をカバーできる。
• `trap 'echo "Error at line $LINENO. Command: $BASH_COMMAND" >> /var/log/myscript.log' ERR` を冒頭に置くことで、失敗した行番号とコマンドをログに残せる。
• `-E`（`-o errtrace`）オプションを合わせて指定すると、サブシェルや関数内でもERRトラップが継承され、深い呼び出しスタックのエラーも捕捉できる。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forward エラーの原因は「別のプロセスがリモートにpushした後、自分がpullせずにcommit→pushしようとした」こと。ローカルとリモートの履歴が分岐している状態。
• 自動化スクリプトでの正しい操作順序は **`git pull --rebase` → ファイル操作 → `git add` → `git commit` → `git push`**。ファイルをコピーしてからpullするとunstaged changesでrebaseがブロックされる。
• `git pull --rebase` はマージコミットを作らずクリーンな線形履歴を保てる。複数の自動化ジョブが同一ブランチにpushする環境では特に有効で、チームでの採用によりマージコンフリクトが30〜40%削減されたという報告もある。
• `git config --global pull.rebase true` を設定すると、以降 `git pull` のデフォルト動作がrebaseになり設定ミスを防げる。

**cronとPATH管理**
• cronジョブはユーザーの `.zshrc`/`.bashrc` を一切読み込まず、PATH は `/usr/bin:/bin` 程度の最小構成のみ。スクリプト冒頭で `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/your/custom/bin` と明示的に宣言するか、crontabファイルの先頭行に `PATH=...` を書くのが最も確実な対策。
• ラッパースクリプトパターンが推奨：環境設定のみ行うシェルを別ファイルにし、そこから本体スクリプトを呼ぶ設計はテスト容易性・保守性が高い。
• macOSでは Apple が launchd を推奨しており、cron は deprecated 扱い。launchd もデフォルト PATH は `/usr/bin:/bin:/usr/sbin:/sbin` の4エントリのみだが、launchctlでの管理・ログ収集・スリープ復帰後の実行補償など cron にない機能を持つ。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は if文・`||`/`&&` チェーン・サブシェル内のエラーを無視するという重大な落とし穴がある。パイプライン内の途中エラーも最後のコマンドの exit code しか見ないため、`set -o pipefail` とセットで使うことが必須。
• 推奨パターンは `set -euo pipefail`：`-u` は未定義変数を空文字展開せずエラー終了させ、`-o pipefail` はパイプ途中の失敗を検知する。さらに `trap 'echo "Error at line $LINENO: exit $?" >&2' ERR` を加えるとコンテキスト付きエラーログが残る。
• `trap ERR` は `set -e` が抑制される条件分岐や `||` チェーン内でも発火するためデバッグ情報収集のカバレッジが広い。失敗ログを残しつつ終了する設計が自動化スクリプトの信頼性を大幅に高める。

**git non-fast-forward と rebase の操作順序**
• 自動化スクリプトでの正しい git 操作順序は `git pull --rebase → ファイル操作 → git add → git commit → git push`。先にファイルをコピーしてから pull すると unstaged changes が rebase をブロックし non-fast-forward エラーの連鎖を招く。
• `git config --global pull.rebase true` をデフォルト設定にすると merge commit が混入しにくくなる。`git config --global rerere.enabled true` を合わせると、過去に解決したコンフリクトを git が記憶して自動適用する。
• force push が必要な場合は必ず `--force-with-lease` を使う。通常の `--force` はリモートの最新コミットを問答無用で上書きするが、`--force-with-lease` はリモートに想定外のコミットがあれば拒否するため、チームメンバーの作業を誤って消す事故を防げる。

**cronとPATH管理**
• cronジョブはユーザーの `.zshrc` や `.bash_profile` を読み込まず、`PATH=/usr/bin:/bin` という最小限の環境で動作する。Homebrew（`/opt/homebrew/bin`）や独自インストールツール（例: claude コマンド）は、crontabの先頭で `PATH=/usr/local/bin:/usr/bin:/bin:/opt/homebrew/bin` と明示的に定義するか、スクリプト内で絶対パスを使うことが必須。`PATH=$PATH:/path` のように変数展開で追記する方法はcron実装によっては機能しないため、フルパスで列挙する。
• macOSではcronよりlaunchdが推奨。cronはMacがスリープ中の実行を完全スキップするが、launchdは起動時に missed execution を検知して即座に実行できる。launchd の plist でも `EnvironmentVariables` に PATH を明示しないと同様の問題が発生するため注意。
• ラッパースクリプト方式が実践的: 本体スクリプトとは別に、環境変数を設定してから本体を呼び出すラッパーを作成し、cronはラッパーを呼ぶ構成にすると、手動でも同じラッパーでテストできて問題切り分けがしやすい。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e`（errexit）は、条件式（`if`、`||`、`&&`）内やパイプラインの途中コマンドの失敗を検知しないという重大な落とし穴がある。`set -e` だけでは「安全そうに見えてサイレント失敗する」スクリプトになる。完全な防御には `set -Eeuo pipefail` の組み合わせが必要: `-u` は未定義変数を検知、`-o pipefail` はパイプ途中の失敗を伝播させる。
• `trap ERR` を `set -E`（errtrace）と組み合わせると、関数内やサブシェル内のエラーにも ERR トラップが継承される。エラーハンドラ関数内で `$?`（終了コード）と `$BASH_LINENO`（行番号）を記録すれば、「どのコマンドが何行目で何のコードで失敗したか」をログに残せる。
• 推奨テンプレート: スクリプト冒頭に `set -Eeuo pipefail` → `trap 'echo "Error at line $LINENO, exit code $?" >&2' ERR` の2行を入れるだけで、サイレント失敗の大半を防げる。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forward エラーの本質は「リモートがローカルの親コミットでない状態でpushしようとした」こと。自動化スクリプトで複数箇所からpushが起きるリポジトリでは、正しい順序は「fetch/pull → 変更作業 → add → commit → push」。変更作業を先に行ってからpullすると、unstaged changes が rebase をブロックして無音終了する。
• `git pull --rebase`（またはglobal設定 `git config --global pull.rebase true`）を使うことで、マージコミットなしで履歴を線形に保てる。force pushが必要になった場合は `git push --force-with-lease` を使う。これはリモートの最新SHAが自分の想定通りの場合のみpushを許可する安全版の force push。
• 自動化でのpre-pushフック活用: `.git/hooks/pre-push` に `git fetch && git rebase origin/main` を仕込むことで、pushの直前に自動でリモートの最新を取り込み、non-fast-forward エラーを事前防止できる。

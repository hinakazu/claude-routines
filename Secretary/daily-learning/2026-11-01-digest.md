**cronとPATH管理**
• cronはユーザーの `.zshrc` / `.bashrc` を読まず、PATHは `/usr/bin:/bin` 程度の最小環境で起動する。`/opt/homebrew/bin` や `/usr/local/bin` は存在しないためコマンドが exit 127 で無音終了する典型的な罠。
• 対策は3段階：①crontabの先頭行に `PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin` を絶対値で明示、②スクリプト内でも同様に宣言、③ `$PATH=$HOME/bin:$PATH` のような変数展開はcrontab内では動作しないため必ず展開後の完全な値を書く。
• macOSではApple公式がcronを非推奨とし **launchd** を推奨。launchdもPATHは最小限のためplistの `EnvironmentVariables` セクションで明示が必要。launchdはPCスリープ中のジョブを再起動後に一度実行する（cronはスキップ）点もメリット。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e`（errexit）は失敗コマンドで即終了するが、`if`文の条件部・`&&`/`||` チェーン・サブシェル内では発動しないという「穴」がある。`let i++` や `((i++))` も値がゼロになった瞬間にexitし、バージョン間で挙動が異なる。
• `set -euo pipefail` を冒頭に置き、`trap 'echo "ERROR: line $LINENO exit $?" >&2' ERR` で失敗行番号を記録するパターンが現代的なベストプラクティス。`-E` フラグ（errtrace）を付けるとERRトラップが関数内にも継承される。
• 「意図的に失敗してよいコマンド」は `|| true` で明示的に握りつぶし、`trap ... EXIT` でクリーンアップを一元化する。`set -e` を使わず全コマンドに手動チェックを付ける方針も選択肢（BashFAQ著者の推奨）。

**git non-fast-forward push と操作順序**
• 自動化スクリプトで `cp → commit → pull → push` と書くと `pull` 時に unstaged changes がありrebaseがブロックされる。正しい順序は **`pull → 変更 → commit → push`**。pushが失敗したら `pull` してから再pushするリトライパターンが推奨（wesleyscholl/git-commit-push-script が実装例）。
• `git pull` の戦略はスクリプト内で `--rebase` か `--ff-only` を明示しておく（設定依存を避けるため）。コンフリクト時はロールバックして終了か、専用ブランチを作って手動解決待ちにするのが安全。autogitプロジェクトはstash→pull→apply→push+コンフリクト時ロールバックを実装した参考実装。
• GitHub公式は non-fast-forward rejection を「リモートの履歴を守るための拒否」と説明。強制pushは絶対に避け、常にfetch/pullでリモートの状態を取り込んでからpushする。

**cronとPATH管理**
• cronはユーザーの `.zshrc` や `.bash_profile` を一切読み込まず、`PATH=/usr/bin:/bin` 程度の最小構成で動く。`$PATH` 変数展開はcron実装によって非サポートの場合があるため、スクリプト冒頭で `/usr/local/bin:/opt/homebrew/bin:/usr/bin:/bin` のようにフルパスを直書きするのが確実。コマンド自体に絶対パス（`/opt/homebrew/bin/claude` 等）を使う方法が最も堅牢。
• macOSではAppleがcronを事実上deprecated扱い。スリープ中にスケジュールされたジョブは実行されず、ウェイクアップ後のリカバリもない。launchdは `EnvironmentVariables` キーでジョブ単位に環境変数を宣言でき、スリープ復帰後のmissed jobs実行にも対応するため、本番自動化ならlaunchdへの移行が推奨。
• 「手元では動くのにcronで動かない」症状の診断手順：`env -i /bin/bash --nologin --norc script.sh` で最小環境を模倣して再現確認し、失敗コマンドに絶対パスを付けて解消できるか確認する。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` 単体は不完全。パイプ内の途中コマンド失敗は伝播せず（`cmd1 | cmd2` でcmd1が失敗してもset -eは反応しない）、`((count--))` のような算術演算は結果が0でも終了コード1を返しスクリプトを突然終了させる。本番スクリプトでは `set -euo pipefail` をセットで使うのが現代の標準。
• `trap 'handler' ERR` でエラー発生箇所をキャッチしてログ記録できる。`set -E`（大文字）を組み合わせるとサブシェル内でも ERRトラップが伝播する。`trap 'cleanup' EXIT` は正常終了・異常終了両方で呼ばれるため、一時ファイルの削除等のクリーンアップに使うと「40%のリソースリーク削減」(ShellCheckユーザー報告) という効果がある。
• 本番パターン：`log() { echo "[$(date +'%F %T')] $*"; }` / `die() { log "ERROR: $*"; exit 1; }` のヘルパー関数を定義し、エラー時に `die "コマンドXが失敗: exit $?"` と明示的にログを残す。2023年のShellCheck調査では `set -euo pipefail` 未使用の本番スクリプトの60%以上でサイレントなデータ損失が発生していた。

**git non-fast-forward pushと操作順序**
• non-fast-forwardエラーはローカルとリモートのブランチ履歴が分岐したときに発生する。自動化スクリプトで複数箇所（人間＋bot）からpushが発生する場合の鉄則は `git fetch → git pull（or rebase）→ ファイル変更 → git add → git commit → git push` の順序厳守。「変更してからpull」の逆順はunstaged changesがrebaseをブロックして無音終了する。
• `git pull --rebase` はローカルコミットを一時退避し、リモートの変更を取り込んだうえでローカルコミットを再適用するため、マージコミットなしで線形履歴を保てる。自動化スクリプトでは `git push` 失敗時に `git pull --rebase && git push` でリトライするパターンが標準（GitHub Actionsの多くのテンプレートもこのパターンを採用）。
• pre-pushフック（Huskyなど）で `git fetch && git rebase origin/main` を自動実行する構成を作れば、pushのたびに最新状態との差分チェックが走り、分岐による失敗をゼロにできる。複数botが同じリポジトリにpushする場合は「プッシュ担当者を1つに限定する」設計も選択肢。

**cronとPATH管理**
• cronジョブはユーザーの `.zshrc` / `.bash_profile` を一切読み込まないため、標準PATHは `/usr/bin:/bin` のみ。`/usr/local/bin` 以下のツール（Homebrew製コマンドなど）はすべて見えない状態になる。回避策はcrontabの先頭に `PATH=/usr/local/bin:/usr/bin:/bin` を宣言するか、スクリプト冒頭で `export PATH=...` を明示すること。
• スクリプト内で `source ~/.bash_profile` を呼ぶ方法もあるが、ログインシェルかどうかによって読み込まれるファイルが変わるため（`.bash_profile` vs `.bashrc`）、PATHを直書きする方が確実で移植性が高い。
• macOSでは `cron` より `launchd` が公式推奨。launchd の `.plist` ファイルには `EnvironmentVariables` キーでPATHを明示的に設定できる。また近年のmacOSプライバシー保護により Desktop/Documents/Downloads へのアクセスが無音失敗するケースがあるため、Full Disk Access権限をターミナル/cron に与えることも必要。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は強力だが「効かない文脈」が多い：`if cmd; then`、`cmd || fallback`、`! cmd` の否定、パイプライン中間の失敗、`local var=$(failing_cmd)` の変数宣言（localのexit codeが上書きする）。これらはすべてサイレントに通り抜けるため、`set -e` だけに頼るのは危険。
• 現代的なベストプラクティスは `set -euo pipefail` の三点セット。`-u` は未定義変数へのアクセスをエラー化、`-o pipefail` はパイプ途中の失敗も捕捉する。さらに `trap 'echo "Error at line $LINENO"' ERR` を加えることで、どこで失敗したか必ずログに残る。
• デバッグ時は `set -x` を追加して `set -euxo pipefail` にすると、実行された全コマンドがステップ表示される。本番では `-x` を外してノイズを減らす。想定内の失敗（`grep` がヒットなしで返す0以外など）は `cmd || true` で明示的にもみ消す。

**git non-fast-forward と自動化スクリプトの操作順序**
• `non-fast-forward` エラーは「ローカルとリモートが分岐していて、ローカル履歴がリモートの全コミットを含んでいない」状態。自動化スクリプトで複数箇所からpushが発生する場合はほぼ確実に踏む。
• 正しい操作順序は `git pull --rebase` → ファイル操作 → `git add` → `git commit` → `git push`。pullを「後から」やると unstaged changes があるため rebase がブロックされる（`error: cannot pull with rebase: You have unstaged changes.`）。
• `git pull --rebase` はマージコミットを作らず履歴を線形に保つためCI/CDや自動化との相性が良い。ただし共有ブランチへのrebaseは禁止（他人のコミットを書き換えてしまう）。自動化スクリプト専用の孤立ブランチか個人のfeatureブランチに限定すること。

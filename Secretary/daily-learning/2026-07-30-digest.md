**cronとPATH管理**
• cronはユーザーの `.zshrc` / `.bash_profile` を一切読み込まないため、PATHは `/usr/bin:/bin` 程度の最小構成になり、Homebrew等でインストールしたコマンドは "command not found" で無音終了する。スクリプト冒頭で `export PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin` のように明示するか、コマンドをフルパスで書くかのどちらかが必須。
• macOSでは cron よりも launchd が推奨。cron はMacがスリープ中だと予定時刻をスキップするが、launchd は起動後にジョブを実行してくれる。Apple Siliconでは `/opt/homebrew/bin` を EnvironmentVariables に追加しないと、Homebrew製コマンドが全滅する。
• デバッグの鉄則は「ログを必ず残す」。crontabのコマンド末尾に `>> /var/log/mycron.log 2>&1` を付けるだけで無音失敗が可視化できる。macOSでは `log show --predicate 'process == "cron"' --last 1h` でシステムログ確認も有効。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` 単独では落とし穴が多い。`if` の条件部・`&&` `||` リスト内・`!` で反転したコマンド・コマンド置換 `$(...)` には伝播しないため、エラーを見逃す。`set -euo pipefail` の3点セットを使うことでパイプ中間のエラーや未定義変数も検出できる。
• `trap 'echo "ERROR at line $LINENO" >&2' ERR` を冒頭に加えると、失敗したコマンドの行番号を標準エラーに出力できる。さらに `trap cleanup EXIT` で終了時に必ずクリーンアップ処理を走らせることで、スクリプトの信頼性が大幅に上がる。
• 算術演算 `(( count-- ))` は結果が0のときに終了コード1を返すため、`set -e` 環境下では意図せずスクリプトが終了する。回避策は `(( count-- )) || true` のように `|| true` を付けるか、`set -e` のスコープ外で計算すること。

**git non-fast-forward push と自動化スクリプトの操作順序**
• non-fast-forwardエラーは「ローカルとリモートが分岐した」状態で発生する。自動化スクリプトでは `cp → commit → push` の直前に `git pull --rebase` を挟まず、かつ unstaged changes がある状態で pull すると rebase がブロックされる。正しい順序は「① stash（または clean）→ ② pull --rebase → ③ ファイル変更 → ④ add + commit → ⑤ push」。
• `git stash` を使えば未コミット変更を一時退避してから pull でき、その後 `git stash pop` で復元できる。自動化スクリプトではこの「stash → pull → pop → commit → push」パターンが最も安全。
• `git pull --rebase` はコミット履歴を線形に保てるが、コンフリクト時に `git rebase --abort` を忘れると中途半端な状態が残る。自動化では `git rebase --abort` をエラーハンドラに組み込み、必ず安全な状態に戻す設計にすること。

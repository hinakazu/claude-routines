**cronとPATH管理**
• cronジョブは最小限の環境（PATH=/usr/bin:/bin のみ）で動作し、.zshrcは読み込まれないため、Homebrewや独自インストールのコマンド（例: `/opt/homebrew/bin`）がexit 127で無音終了する。スクリプト冒頭で `export PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin` と絶対パスで明示指定するのが最も確実。
• crontab内での `PATH=$PATH:/custom/path` のような変数展開は多くのcron実装で非対応。必ずフルパスで列挙すること。
• macOSでは `launchd`（plistファイルでジョブ定義）の方がcronより優れる。理由①: plist内で環境変数を個別に宣言できる。理由②: スリープ中の実行を検知して復帰後に自動リトライする（cronは見逃す）。定期自動化には `launchd` への移行を検討する価値がある。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` はif/while条件部・`&&`/`||`リスト内・パイプ中間コマンドでは機能せず、失敗しても続行してしまう。例: `false && true` はexit 0として扱われる。信頼できるのは `set -euo pipefail` の三点セットで使う場合のみ。
• コマンド置換（`out=$(false)`）内では `set -e` が継承されない。これを解決するには `-E`（errtrace）オプションが必須: `set -eEuo pipefail`。サブシェル内エラーもERRトラップが受け取るようになる。
• 推奨パターン: スクリプト冒頭に `set -eEuo pipefail` を書き、`trap 'echo "ERROR: line $LINENO, cmd: $BASH_COMMAND, exit: $?" >&2' ERR` でエラー発生箇所をログ出力。無音終了を完全に排除できる。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forwardエラーの根本原因は「リモートに自分の知らないコミットが追加された後にpushしようとした」こと。自動化スクリプトで複数箇所（手動+cron）から同一リポジトリにpushする場合に特に頻発する。
• 正しい操作順序は `git pull --rebase origin <branch>` → ファイル操作（cp等） → `git add` → `git commit` → `git push`。誤った順序（ファイル操作→pull→commit→push）だとunstaged changesがあるためrebaseが中断されブロックされる。
• 自動化スクリプトでの推奨パターン: `git stash -u` → `git pull --rebase` → `git stash pop` → コミット → `git push --force-with-lease`（`--force`より安全）。また、pre-pushフック（Husky等）でpush前に自動fetchを走らせると事故を防ぎやすい。

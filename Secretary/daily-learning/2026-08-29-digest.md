**cronとPATH管理**
• cronジョブはユーザーの`.zshrc`を読み込まず、デフォルトPATHは`/usr/bin:/bin`という最小環境。HomebrewやNode.js等のバイナリが見つからず`exit 127`でサイレント終了する典型的な罠。
• 解決策は3層：①crontabファイル冒頭に`SHELL=/bin/bash`と`PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/path/to/custom`を明示、②スクリプト内でコマンドの絶対パスを使う、③ラッパースクリプトで環境変数セットアップを分離する。
• macOSではlaunchdがcronの後継。SIPとの統合、スリープ復帰後のジョブ実行など現代のmacOS事情に対応しており、新規自動化はlaunchd（`.plist`ファイル）を使うのが推奨。

**`set -e`のサイレント終了とエラーハンドリング設計**
• `set -e`はif/while/until条件式、`||`/`&&`チェーン、サブシェル内では発火しないという重大な盲点がある。`(( i++ ))`のような算術式がゼロ評価されても終了するため、意図しない動作が起きやすい。
• より信頼性の高い方法は`trap 'error_handler $LINENO "$BASH_COMMAND" $?' ERR`。ERRトラップはこれらすべての文脈で発火し、失敗行番号・コマンド・終了コードをログに残せる。`set -E`（errtrace）と組み合わせると関数やサブシェル内でも継承される。
• プロダクション推奨パターン：スクリプト冒頭に`set -euo pipefail`＋`trap 'echo "Error at line $LINENO: $BASH_COMMAND (exit $?)" >&2' ERR`を置き、EXITトラップでクリーンアップを実行する。

**git non-fast-forwardとrebaseの操作順序**
• 自動化スクリプトで複数箇所からpushが発生すると「Not possible to fast-forward」が頻発する。根本原因はファイル操作後にpullするという順序ミスで、unstaged changesがあるとrebaseがブロックされる。
• 正しい操作順序は`git pull --rebase` → ファイル操作・編集 → `git add` → `git commit` → `git push -u origin <branch>`。2025年の推奨サイクルは「pull → validate → commit → push」。
• `git pull --rebase`はローカルコミットをリモートの最新コミットの上にreplayするため線形履歴を保てる。コンフリクト時は`git add .` → `git rebase --continue`で段階的に解消する。

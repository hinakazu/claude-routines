**cronとPATH管理**
• cronジョブはユーザーの`.zshrc`や`.bash_profile`を一切読み込まず、`PATH=/usr/bin:/bin`という最小構成のみで起動する。Homebrewやnvmなど独自パスのツールは "command not found (exit 127)" で無音失敗する
• 最も確実な対策はスクリプト冒頭で明示的に記述する方式：`PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin; export PATH`。crontabファイル内での変数展開（`PATH=$PATH:...`）はcron実装によって動かないため、フルパスを直書きすること
• macOSではAppleがcronよりlaunchdを推奨。launchdのPlistで`EnvironmentVariables`キーを使えばジョブごとに環境変数を宣言でき、スリープ中に実行できなかったジョブも次回起動時に自動再実行される（cronにはこの機能がない）

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e`の3大落とし穴：①`$(cmd)`などコマンド置換内のエラーは親シェルに伝播しない、②パイプ`A | B`では最後のコマンドBの終了コードのみ評価される（Aが失敗しても無視）、③`if`/`while`/`until`の条件式内では`set -e`は発動しない
• ベストプラクティスは`set -euo pipefail`の3点セット：`-u`は未定義変数をエラー扱いに、`-o pipefail`はパイプ内エラーを捕捉。さらに`set -E`（大文字）を加えるとtrapがサブシェルでも確実に動作する
• `trap 'echo "ERROR: line $LINENO, exit $?" >> /path/to/error.log' ERR`でエラー発生行番号と終了コードをログに記録。本番スクリプトは`trap cleanup EXIT`も必須（正常終了・エラー・Ctrl+C すべてでcleanup関数を実行）

**git non-fast-forward push と rebase の操作順序**
• `git rebase`はworking directoryがクリーンでないと `"cannot rebase: unstaged changes"` でブロックされる。自動化スクリプトで `cp → pull → commit → push` の順にすると、cpで生成したファイルがunstagedの状態でpullが失敗するパターンにはまりやすい
• 最も安全な自動化解決策は`git rebase --autostash`：stash→rebase→stash popを自動実行。グローバル設定`git config --global rebase.autoStash true`で全リポジトリに適用できる
• 自動化スクリプトの推奨操作順序：`git stash -u → git pull --rebase → [ファイル操作] → git add → git commit → git push`。また`git config --global pull.rebase true`でpull時のデフォルトをrebaseにし、不要なmerge commitを防ぐ

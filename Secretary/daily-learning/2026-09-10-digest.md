**cronとPATH管理**
• cronジョブはユーザーの `.zshrc`/`.bashrc` を読まないため、PATHは `/usr/bin:/bin` のみの最小限環境で起動する。Homebrew（`/opt/homebrew/bin`）や独自インストールのCLIツールは自動的に見つからず、exit 127で無音終了する。
• 解決策は3つ: (1) crontabの先頭に `SHELL=/bin/bash` と完全なPATHを明示（`PATH=$PATH:/...` の変数展開は不可・実装依存）、(2) スクリプト冒頭で `export PATH=...` を記述するラッパースクリプト方式、(3) すべての実行ファイルに絶対パスを使用。
• macOSではAppleがcronを公式に非推奨とし、launchdへの移行を推奨。launchdは `EnvironmentVariables` キーで各エージェント独立のPATHを設定でき、スリープ復帰時のmissed job実行やSIPとの連携も優れる。Apple Silicon Macでは `/opt/homebrew/bin` の追加が必須。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e`（errexit）はコマンド失敗時に即終了するが、`&&`/`||` チェーン内・`if`/`while`/`until` の条件部分・パイプライン途中のコマンドでは**発動しない**。`call && true` は失敗してもスクリプトが継続してしまう代表例。
• 推奨パターンは `set -eEo pipefail` + `trap ERR` の組み合わせ。`-E`（errtrace）でサブシェル内でもERRトラップが継承される。`trap cleanup EXIT` で一時ファイル削除・BGプロセス終了を確実に実行。
• 根本原則：`set -e` を唯一の安全網にしない。失敗行番号を残す `trap 'echo "Error on line $LINENO (exit $?)" >&2' ERR` パターンがsilent failure調査に有効で、`set -e` がなくても動作するコードを書くことが信頼性の基礎。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forwardエラーは、ローカルにないリモートコミットが存在するときに発生。自動化スクリプトが複数箇所から同一ブランチにpushする環境（CIの自動コミット等）で特に頻発する。
• 正しい操作順序は「pull → 変更 → commit → push」。`cp（ファイルコピー）→ commit → pull` のように変更後にpullすると、unstaged changesがある状態でrebaseが走りブロックされる。
• 自動化スクリプトでの基本は `git pull --rebase origin <branch> && git push`。より安全にするには `git fetch origin && git stash -u && git rebase origin/<branch> && git stash pop && git push` の順序でuntracked filesも含めてクリーンに扱える。小さく・頻繁にpushして乖離ウィンドウを縮小するのがベストプラクティス。

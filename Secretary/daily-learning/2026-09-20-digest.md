**cronとPATH管理**
• cronジョブはユーザーの`.bashrc`/`.zshrc`を読み込まないため、インタラクティブシェルとは別のPATH環境で実行される。crontabファイル冒頭に`PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`と明示するのが確実。`$PATH`のような変数展開はcron実装によって文字通りに解釈されるため使わない。
• macOSでは`launchd`がcronの推奨代替。`EnvironmentVariables`キーで`PATH`を明示でき、Apple Silicon MacではHomebrew用に`/opt/homebrew/bin`を追加する必要がある。launchdはスリープ中にスキップしたジョブをウェイク後に補完実行できるが、cronはスキップしたジョブを再実行しない。
• デバッグ最短手順：スクリプト冒頭に`env > /tmp/cron-env.log`を入れてcron実行時の環境変数全体をダンプし、どのPATHで動いているか確認する。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e`は`if`文・`||`・`&&`チェーン・サブシェル内では発火しない盲点がある。パイプラインの中間エラーも拾えないため`set -o pipefail`と組み合わせること。推奨は`set -euo pipefail`の3点セット（exit-on-error + 未定義変数エラー + パイプライン失敗検知）。
• ERRトラップでエラー行番号をログに残すのが堅牢な設計：`trap 'echo "Error on line $LINENO, exit $?" >> /tmp/script.log' ERR`。`set -eE`にするとERRトラップがサブシェルや関数内でも発火する。
• デバッグには`bash -x script.sh`または`set -x` / `set +x`で問題箇所だけトレースを有効化する。サイレント終了の原因特定はこの組み合わせが最速。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forwardエラーの根本：ローカルHEADがリモートの最新コミットの祖先でなくなった状態でpushしようとしている。複数箇所から同一リポジトリにpushする自動化スクリプトで頻発する典型パターン。
• 安全な操作順序：`git stash -u`（未ステージ変更を退避）→ `git pull --rebase`（リモート変更を取り込む）→ ファイル更新処理 → `git add` → `git commit` → `git push`。stash前にpull/rebaseすると未コミット変更がrebaseをブロックする。
• 共有ブランチへのrebaseは禁止（コミットIDが変わり他者のチェックアウトを破壊する）。自動化スクリプトで使うブランチは自分専用pushに限定するか、`git merge`（non-rebase）で取り込む方針を徹底する。

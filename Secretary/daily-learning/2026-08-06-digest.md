**cronとPATH管理**
• cronは `.zshrc` / `.bashrc` を一切読み込まず、`/usr/bin:/bin` 程度の最小PATHで動作する。`claude` や `brew` などのツールが exit 127 で無音終了する典型的な原因。対策はcrontab先頭に `SHELL=/bin/bash` と完全なPATHを明示すること（`PATH=$PATH:/追加パス` の変数展開はcron実装によって展開されないため必ず完全パスで書く）。
• macOSではcronより **launchd** が適切：plistの `<key>EnvironmentVariables</key>` にPATHを宣言でき、Apple Silicon Macは `/opt/homebrew/bin` の追加が必須。またlaunchdはスリープ中のジョブをwake後に実行できるが、cronはスリープ中のジョブをスキップして次回まで待つ（ラップトップ環境での大きな差）。
• スクリプト自体の先頭にも `#!/bin/bash` + `PATH=/usr/local/bin:/usr/bin:/bin:...` を書くことで、cronとlaunchdのどちらから呼ばれても確実に動作する二重の防御になる。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は `if`/`elif` の条件部・`while`/`until` のループ条件・`&&`/`||` パイプラインの中間コマンド・`!` 反転条件では **機能しない**。また `$(...)` コマンド置換内でもデフォルトでは継承されず、`set -e -o inherit_errexit` を付けることで初めて置換内のエラーも検知できる。
• 推奨構成は `set -euo pipefail` + `set -E`（errtrace）+ `trap 'handle_error "$?" "$BASH_COMMAND"' ERR` の三点セット。`-E` を付けることでERRトラップが関数・サブシェルにも継承される。ログにはコマンド名・終了コード・行番号を含めると原因特定が速い（`echo "ERROR: $BASH_COMMAND exited with $?" >> /tmp/script.log`）。
• `set -e` はあくまで「補助的な安全装置」であり、メインのエラー処理機構ではない。意図的に失敗を許容するコマンドは末尾に `|| true` を付け、trap ERRで全失敗をキャッチしてログに記録するパターンが本番スクリプトの標準設計。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forwardエラーはリモートブランチがローカルのcommitの祖先でない時に発生する。複数箇所（ローカルPC・CIジョブ・別マシン）からpushが行われる自動化リポジトリで起きやすい。正しい操作順序は **`git pull --rebase` → ファイル操作 → `git commit` → `git push`** の一択。pull前にunstaged changesがあると rebase がブロックされるため、スクリプトでは必ず `git stash` または commit 後に pull する。
• `git pull --rebase` はローカルのcommitをリモートの最新に積み直すことでhistoryを線形に保つ。merge型の `git pull` はマージコミットを生成するため自動化スクリプトでは避けるのが一般的。
• 強制pushが必要な場合は `--force-with-lease` を使う（`--force` は禁止）。`--force-with-lease` はリモートに自分が知らない新コミットがある場合は自動中断するため、チームメンバーの作業を上書きするリスクがない。

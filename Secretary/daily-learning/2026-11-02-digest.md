**cronとPATH管理**
• cronはユーザーの `.zshrc` や `.bashrc` を読み込まないため、デフォルトのPATHは `/usr/bin:/usr/sbin` 程度しかない。`/Applications/cmux.app/Contents/Resources/bin` のようなアプリ固有パスは未登録になり、コマンドがexit 127で無音終了する。
• 対策は3層で考える：①スクリプト冒頭に `export PATH="/usr/local/bin:/opt/homebrew/bin:$PATH"` を明記する、②コマンドはフルパス（`/usr/local/bin/claude`）で書く、③crontabファイル先頭に `PATH=...` 行を書いて全ジョブに適用する。
• デバッグには `* * * * * env > /tmp/cron_env.log` のダミージョブで実際のcron環境変数を可視化する方法が有効。`/etc/environment` に書いた変数はcronに渡るが、cronが独自に設定するPATH変数は渡されない点に注意。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e`（errexit）はコマンド失敗時に即スクリプト終了するが、`if`/`while` の条件部・`!` で否定されたコマンド・サブシェル内（`$(...)` コマンド置換）では発火しない。`export VAR=$(false_cmd)` のような宣言組み込みコマンドも失敗を隠す。
• 推奨パターンは `set -Eeuo pipefail` の組み合わせ：`-E` で ERR トラップをサブシェルに継承、`-u` で未定義変数をエラー化、`-o pipefail` でパイプ中間コマンドの失敗を検知。ERR トラップで `echo "ERROR: line $LINENO, exit $?" >> /var/log/script.log` のようにログを残す。
• 予期した失敗は `cmd || true` または `set +e; cmd; set -e` ブロックで明示的に処理し、`set -e` の例外ケースに依存しない設計にする。Bash 4.4以降は `inherit_errexit` オプションで `$()` 内も errexit を継承できる。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forward エラーはリモートに自分が持っていないコミットが存在する状態でpushすると発生する。自動化スクリプトで複数箇所からpushする場合（cronとローカル手動操作の混在など）は特に頻発する。
• 正しい操作順序：`git fetch origin <branch>` → ローカル変更（ファイルコピー等） → `git add` → `git commit` → `git pull --rebase origin <branch>` → `git push`。変更前にfetchしていても、pushまでの間に別のpushが入る可能性があるため、push直前にも `--rebase` を実行するのが安全。
• 自動化では `--force-with-lease`（リモートの最新状態を確認してから強制push）を使う選択肢もあるが、基本はfetch→rebase→pushのリトライループを実装する。`pull.rebase=true` をgit configに設定しておくと `git pull` が自動的にrebaseモードになる。CI botが並行してpushするリポジトリではこの競合が特に多い。

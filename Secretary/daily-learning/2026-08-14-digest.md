**cronとPATH管理**
• cron起動時は `~/.zshrc` が読み込まれず、デフォルトPATHは `/usr/bin:/bin` のみ。Homebrew等の `/opt/homebrew/bin` は未登録になり「command not found」で無音終了する。
• 解決策は3段階：①スクリプト冒頭で `PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin` と明示宣言 ②crontabファイル先頭行に `PATH=...` を記述（全ジョブに適用） ③環境セットアップ用ラッパースクリプトを挟む。
• macOSでは cron より **launchd** が推奨。plistの `EnvironmentVariables` キーでPATHを指定でき、スリープ/ウェイク後のmissed job実行も可能。Apple Siliconでは `/opt/homebrew/bin` を必ず追加し、パスに `~` は使えないため `/Users/yourname/` と書く。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は `&&`/`||` チェーン・`if`条件部・パイプ途中コマンドでは発動しない。`call && true` は失敗しても続行するが `true && call` は停止するという非直感的な挙動がある。コマンド置換 `$( )` 内では `set -e` が継承されず、`inherit_errexit` オプションが必要。
• 推奨パターンは `set -eE` + `trap ERR` の組み合わせ。`-E`（errtrace）を加えると関数・サブシェル内にもERRトラップが伝播する。失敗コマンド名・終了コード・行番号をログに残すハンドラを登録することでサイレント失敗を防ぐ。
• 設計原則：`set -e` のみに依存しない。`trap ERR` による明示的ハンドラを基本設計とし、`trap cleanup EXIT` でテンポラリファイル・バックグラウンドプロセスを確実にクリーンアップする。

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトでの正しい操作順序は `git pull --rebase origin main` → ファイル変更 → `git commit` → `git push`。pullを後回しにすると unstaged changes があるときにrebaseがブロックされてpushが失敗する。
• `git config --global pull.rebase true` でデフォルトをmergeからrebaseに変更するとマージコミットが発生せず履歴が直線的に保たれる。rebase後のpushは `--force` ではなく `--force-with-lease` を使う（リモートに想定外のコミットがあればpushを拒否するため安全）。
• pre-pushフックで `git fetch && git rebase` を自動化するパターンが2025〜2026年のベストプラクティスとして広まっている。共有ブランチ（main等）にpush済みコミットをrebaseするのは禁止（チーム全員が強制pull/re-cloneを強いられる）。

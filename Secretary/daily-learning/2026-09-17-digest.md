**cronとPATH管理**
• cronジョブはユーザーの `.zshrc` や `.bashrc` を読み込まないため、Homebrewや独自インストールのパスが未登録となり `command not found`（exit 127）で無音終了する。スクリプト冒頭で `PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:$PATH` のように明示的にPATHを定義することが最善策。
• macOSではAppleがcronを非推奨にしており、launchdへの移行が推奨されている。launchdはPListファイル内でジョブごとに `EnvironmentVariables` を宣言でき、shell設定に依存しない安全な環境変数管理が可能。macOS Sequoiaでもcronは後方互換で動作するが、新規構築にはlaunchdが望ましい。
• 本番環境では「環境設定用ラッパースクリプト」パターンが有効：実際のジョブスクリプトとは別にPATH/ENVを設定するラッパーを用意し、テスト・ドキュメント・自己説明性を確保する。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は条件式（`if`）・論理演算子（`||`/`&&`）・サブシェル（`$(...)`）の中ではエラー時に終了しない盲点がある。これにより「失敗しているのに続行する」という見えにくいバグが発生する。
• `trap 'echo "ERROR line:$LINENO cmd:$BASH_COMMAND" >> /var/log/err.log' ERR` のようにtrapでエラーを捕捉することで、どのコマンドが何行目で失敗したかをログに残せる。`set -E`（errtrace）と組み合わせると関数やサブシェル内のエラーもtrapが継承される。
• 推奨パターン：`set -euo pipefail` + `set -E` + `trap '...' ERR` + `trap cleanup EXIT` の4点セット。pipefailはパイプ中間コマンドの失敗も捕捉し、EXITトラップは異常終了時のクリーンアップを保証する。

**git non-fast-forward push と rebase の操作順序**
• 「手動では動くのにスクリプトで失敗する」git問題の典型はステップ順序ミス。ファイルコピー後にpullを実行すると未コミットの変更が残りrebaseがブロックされる。正しい順序は `pull（最新取得）→ ファイル変更 → add → commit → push`。
• 複数箇所からpushが発生するリポジトリでは `git config pull.rebase true` を設定に追加しておくことで、merge commitを生成せずにlinearな履歴を維持できる。自動化スクリプトでは `git pull --rebase` を明示的に書くほうが設定依存せず安全。
• push失敗時のリトライ設計として「pushが失敗したらpullしてから再push」というループを組み込むことで、自動化スクリプトの競合耐性が高まる。`git push || (git pull --rebase && git push)` のような短絡評価パターンが実用的。

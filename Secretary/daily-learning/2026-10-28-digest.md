**cronとPATH管理**
• cronジョブはユーザーの `.zshrc` / `.bashrc` を読み込まないため、`/usr/local/bin` 等はデフォルトのPATHに含まれない。スクリプト冒頭に `export PATH=/usr/local/bin:/usr/bin:/bin:$PATH` と明示するのが最も確実な解決策
• `env > /tmp/cron-env.txt` をcronから実行してインタラクティブシェルのenvと比較するのがデバッグの定石。何がPATHから抜けているか一目でわかる
• macOSではcronよりlaunchd（LaunchAgents）が推奨。plistの `EnvironmentVariables` キーでPATHを明示設定できる。Sequoia以降ではcronジョブがサイレントスキップされる報告もあり、launchdへの移行が安全

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -euo pipefail` がプロダクションスクリプトの標準設定。`-e`（コマンド失敗で即終了）＋`-u`（未定義変数でエラー）＋`-o pipefail`（パイプ途中の失敗も検知）の3つをセットで使う
• 代表的な罠：`local var=$(command)` は `local` コマンドの終了コードが `command` の失敗を隠す。`local var; var=$(command)` と2行に分けることで回避できる
• `trap 'echo "ERROR at line $LINENO: $BASH_COMMAND" >&2' ERR` でどのコマンドが失敗したか行番号付きでログに残せる。サブシェルにも伝播させるには `set -E` を追加する

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトでの正しい操作順序：`git add → git commit → git pull --rebase --autostash → git push --force-with-lease`。pull前にunstaged changesがあるとrebaseがブロックされるため、必ずcommit後にpullする
• `--autostash` オプションを使うとpull前に自動stash・pull後に自動popするため、unstaged changesがあっても安全にpullできる。CI/CDパイプラインで特に有効
• 複数箇所からpushが発生するリポジトリでは `git config pull.rebase true` を設定しておくことで常にrebaseベースでpullされ、不要なmerge commitが履歴に残らない

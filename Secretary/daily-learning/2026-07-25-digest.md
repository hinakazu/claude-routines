**cronとPATH管理**
• cronジョブはユーザーの `.zshrc` を読み込まず、PATHが `/usr/bin:/bin` 程度に限定される。解決策は①crontab冒頭で `PATH=/usr/local/bin:/usr/bin:/bin` と明示指定、②ラッパースクリプトでPATHを設定してから実際のコマンドを呼ぶ、の2択。変数展開 `PATH=$PATH:/追加パス` は一部のcron実装で機能しないため使用不可。
• macOSでは2005年からcronはAppleによって非推奨扱いで、launchdが公式代替。launchdのplistファイルで `<key>EnvironmentVariables</key>` セクションにPATHを直接記述でき、Apple Silicon環境では `/opt/homebrew/bin` も必ず追加が必要。
• cronはMacがスリープ中にジョブ時刻を過ぎると次回まで実行されないが、launchdは起動後に未実行ジョブを検知して即実行する機能を持つ。定期自動化の信頼性という観点でもlaunchdが優位。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は条件式の一部（`cmd || echo fail`）、`local var=$(failing_cmd)` のコマンド代入、サブシェル内エラーなど複数のシナリオでは発火しない。`((count++))` は変数が0のとき「前値0＝失敗」として即exitする罠があり、`count=$((count + 1))` か `((count++)) || true` に書き換えが必要。
• 推奨設定は `set -eEuo pipefail` の組み合わせ。`-E` によりERRトラップが関数・サブシェルに継承され、`-u` が未定義変数をエラーに、`pipefail` がパイプ途中の失敗も伝播させる。エラーログは `trap 'echo "Error at line $LINENO. Command: $BASH_COMMAND" >> /tmp/script.log' ERR` で行番号・コマンド名付きで記録できる。
• 原因追跡には `bash -x script.sh` の実行トレースが最速。エラーを無視したい特定コマンドには `|| true` を末尾に付けるのが標準的な慣習。`set -e` 単体は「安全に見えてデバッグを難しくする諸刃の剣」であり、必ずtrapとセットで運用する。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forward エラーの根本原因は「リモートにローカルが持っていない新しいコミットがある状態でpushを試みた」こと。正しい操作順序は `git pull --rebase origin <branch> → 変更作業 → git commit → git push`。変更前にpullしないと未ステージ変更でrebaseがブロックされる。
• 自動化スクリプトでの安全なpushは `--force-with-lease` を使う。`--force` と異なりリモートに未取得コミットがある場合は拒否されるため、チームの作業を上書きする事故を防ぐ。non-fast-forward が発生したら `git pull --rebase` 後にリトライするロジックを組み込む。
• `pre-push` hookで事前に `git fetch --dry-run` を実行してリモートとの差分を検知する設計も有効。Gitの状態機械（未追跡→ステージング→コミット→プッシュ）を自動化スクリプト内で明示的に段階管理することで同種のバグを防止できる。

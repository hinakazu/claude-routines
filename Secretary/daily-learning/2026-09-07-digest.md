**cronとPATH管理**
• cronジョブはユーザーの .zshrc/.bashrc を読み込まず、PATH=/usr/bin:/bin という最小環境で起動する。HomebrewやApple Silicon向けの /opt/homebrew/bin、独自ツールのパスは全て未登録になるため、スクリプト冒頭でPATHを完全に明示するか、コマンドを絶対パスで書く必要がある。
• macOSでは cron は非推奨で、Apple公式のスケジューラは launchd。launchd はEnvironmentVariablesキーでPATHを宣言でき、スリープ後に実行漏れを自動リカバリできる。cron はスリープ中の実行をサイレントスキップするだけ。
• 自動化スクリプトでのPATH安全設計3パターン：①crontabファイル先頭に `PATH=/full/path:...` を直書き、②スクリプト先頭で `export PATH="/full/path:$PATH"` を実行、③.envファイルにまとめてスクリプト冒頭でsource。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は「失敗したら即終了」だが、if文・||/&&チェイン・サブシェル内では抑制される。`((i++))` のように 0 を返す算術式でもスクリプトが終了するなど、意図しない挙動が多い。
• 安全なパターンは `set -euo pipefail` + `trap 'echo "Error at line $LINENO: $BASH_COMMAND" >&2' ERR`。さらに `set -E`（errtrace）を追加すると、関数やサブシェルでも ERR トラップが継承される。
• 本格的なエラーログには `BASH_LINENO` 配列と `BASH_SOURCE` 配列を組み合わせてスタックトレースを出力できる。`2>logfile` でファイルに残し、`set -x` と組み合わせると原因特定が大幅に速まる。

**git non-fast-forward push と操作順序**
• 複数端末や自動化スクリプトが同一ブランチにpushする場合、正しい順序は「fetch → rebase（またはpull --rebase）→ 変更 → commit → push」。変更後に pull しようとすると unstaged changes が rebase をブロックする。
• `git config pull.ff only` を設定すると、fast-forwardでない状況では pull 自体が失敗し、意図しないマージコミットの生成を防げる。自動化スクリプトに最も安全な設定。
• CI/CDの自動コミット（semantic-release等）後は必ず pull が必要。2026年のGitOpsベストプラクティスでは「変更前fetch・push後に他のジョブがpull」というルールを設計レベルで決めておくことが推奨されている。

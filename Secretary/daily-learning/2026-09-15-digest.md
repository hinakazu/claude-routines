**cronとPATH管理**
• cronジョブのデフォルトPATHは `/usr/bin:/bin` のみで、`.zshrc` や `.zprofile` は一切読み込まれない。HomebrewやApp内のツール（`/opt/homebrew/bin`, `/Applications/xxx.app/Contents/Resources/bin`）は未登録のままコマンドがexit 127でサイレント終了する。
• macOS Sequoia/Tahoe以降ではAppleがcronデーモンをユーザーセッションからさらに切り離しており、launchdも「ProgramArgumentsは配列形式」でなければ無音失敗する。修正パターンは①スクリプト冒頭で `PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin` を明示 ②コマンドは絶対パスで記述 ③`.env`ファイルをsourceする、の3択。
• launchdはログパス（StandardOutPath / StandardErrorPath）を設定しないと失敗が完全に見えない。自動化スクリプトには必ずログ出力先を指定すること。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は `if`/`elif`の条件部分・`&&`/`||`チェーン内・パイプラインの非末尾コマンド・コマンド置換 `$(...)` 内では**発動しない**。`true && fail_cmd` は失敗するが `fail_cmd && true` は失敗しないなど直感に反する挙動が多い。
• 堅牢な組み合わせは `set -eE`（`-E`=errtrace）＋ `trap 'echo "ERROR: line $LINENO, exit $?" >&2' ERR` ＋ `trap cleanup EXIT`。これにより関数・サブシェル内のエラーもトラップし、終了コードとエラー行番号をログに残せる。
• パイプラインの途中コマンドのエラーを捉えるには `set -o pipefail` も必須。`set -eEo pipefail` をセットで使うのが2025〜2026年のベストプラクティスとして定着している。

**git non-fast-forward と自動化スクリプトの操作順序**
• non-fast-forward エラーは「リモートに自分がまだ持っていないコミットがある状態でpushしようとした」ときに発生。複数箇所（手動操作・CI・他の自動スクリプト）がpushするリポジトリで特に起きやすい。
• 自動化スクリプトでの正しい操作順序は `git pull --rebase` → ファイル操作 → `git add` → `git commit` → `git push`。ファイルコピー後にpullすると unstaged changes で rebase がブロックされる。
• push失敗時のリトライ戦略として、終了コードが non-fast-forward の場合のみ `git pull --rebase` → 再push するループを最大数回実施するのが自動化スクリプトのパターン。`git config pull.rebase true` をグローバル設定しておくと `git pull` だけでrebaseになり安全。

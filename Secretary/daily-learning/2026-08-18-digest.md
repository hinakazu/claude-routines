**cronとPATH管理**
• cronジョブが使うデフォルトPATHは `/usr/bin:/bin` のみ。`.bashrc`/`.zshrc` は読み込まれないため、`nvm`・`claude` など独自インストールのバイナリが exit 127 で無音終了する。
• 根本的対策は2つ: crontabファイルの先頭に `SHELL=/bin/bash` と `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin` を明示的に記載する方法、またはラッパースクリプト内で `export NVM_DIR="$HOME/.nvm" && source "$NVM_DIR/nvm.sh"` のように環境を初期化してから本体スクリプトを呼ぶ方法。
• `$PATH` のような変数展開はcrontab内では動作しない実装があるため、パスは必ず絶対値でフルパス記述すること。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` だけでは不十分。条件式 (`if cmd; then`)・`||`/`&&` チェーン・サブシェル内では `set -e` が無効化され、コマンド失敗でも終了しない。パイプライン内の中間コマンドの失敗も見逃す（最後のコマンドが成功すれば `$?=0`）。
• 推奨テンプレートは `set -euo pipefail` + `trap 'echo "Error at line $LINENO, cmd: $BASH_COMMAND, exit: $?" ERR'` + `trap cleanup EXIT` の3点セット。`-E` オプションを加えると関数・サブシェル内でもERRトラップが継承される。
• ログは `2>> /var/log/myscript.log` でファイルに書き、`set -x` をデバッグ時に有効化するとコマンドを実行前に出力できるため原因特定が格段に速くなる。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forward エラーはローカルのコミット履歴がリモートブランチの先端を含んでいない場合に発生する。複数箇所からpushが走る自動化スクリプトでは特に頻発する。
• 安全な操作順序は「① pull（rebase） → ② 変更ファイルのコピー/生成 → ③ git add & commit → ④ push」。`cp → commit → pull → push` の順だとpull時に未コミット変更が残り rebase がブロックされる典型的なバグになる。
• 自動化スクリプトではpush失敗時に "non-fast-forward" を検出してpull → リトライするロジックを入れると堅牢になる。ただし共有ブランチへのrebaseは絶対に避ける（コミットハッシュが変わり他の作業者を壊す）。

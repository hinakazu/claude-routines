**cronとPATH管理**
• cronジョブはユーザーの `.zshrc`/`.bashrc` を読み込まないため最小限のPATHのみが設定される。`/Applications/xxx/bin` などのカスタムパスはすべて未登録になり `exit 127` でサイレント失敗する
• 解決策は3択：①crontab冒頭で `PATH=/usr/local/bin:/usr/bin:...` を明示定義、②ラッパースクリプトでPATHを設定してから呼び出す、③`.profile` を source する（crontab内での変数展開は不可）
• macOS Sequoia以降ではcronデーモンが事実上動作しないケースがある。macOS公式推奨はlaunchdへの移行で、スリープ中にスキップされたジョブのキャッチアップ実行も可能

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` はパイプライン内・条件式内・サブシェル (`output=$(false)`) の失敗を無視する。「安全装置」に見えてデバッグを困難にする諸刃の剣
• 本番スクリプトの業界標準は `set -euo pipefail` の3点セット：`-e`（非ゼロで即終了）、`-u`（未定義変数をエラー扱い）、`-o pipefail`（パイプライン途中の失敗を伝播）
• `trap 'echo "Error at line $LINENO"' ERR` でエラー発生行をログに残す。デバッグ時は `bash -x` または `PS4='+(${BASH_SOURCE}:${LINENO}): '` でトレース出力をリッチ化

**git non-fast-forward と自動化スクリプトの操作順序**
• non-fast-forwardエラーはリモートが自分のローカルの先祖でなくなった（他者がpushした）ときに発生。Gitのデータ損失防止機能で、正しい対処は fetch → integrate → push の順序を守ること
• 自動化スクリプトでは `git pull --rebase --autostash` が有効。未コミット変更を自動退避・再適用しつつリモートの最新状態に追従できる。GitHub Actionsでも同パターンが定番
• 自分のfeatureブランチのみ `git push --force-with-lease` は許容されるが、共有ブランチへのforce pushは禁止。`--force-with-lease` は他者の変更を上書きしない安全なforce push

**cronとPATH管理**
• cronやlaunchdはユーザーの `.zshrc` / `.zprofile` を読み込まないため、Homebrew・バージョンマネージャ経由でインストールしたツール（node, python3, claude等）がPATH未登録でexit 127のまま無音終了する。防止策は crontab の先頭行に `PATH=...` を明示するか、スクリプト内でフルパス指定すること。
• macOSのlaunchdは `~` を展開しないため、ログパスや WorkingDirectory に `~/` を使うとジョブ起動前にサイレント失敗する。`/Users/yourname/` と絶対パスで書く必要がある。
• デバッグの鉄則は「cronが受け取る環境変数をキャプチャして手動実行と比較すること」。一時ジョブで `env > /tmp/cron_env.txt` を実行すると実際のPATHが確認できる。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は `if` 文・`||` / `&&` チェーン・サブシェル内では無効化されるため、「失敗しても終了しない」ケースが多発する。安全な出発点は `set -Eeuo pipefail`（e=即終了、E=ERRトラップをサブシェルに継承、u=未定義変数エラー、pipefail=パイプ途中の失敗を伝播）。
• `trap 'echo "ERROR at line $LINENO, exit=$?" >&2' ERR` を冒頭に置くだけで、サイレント終了時の行番号と終了コードがログに残る。`set -E` がないと関数内のERRトラップが発火しない点に注意。
• デバッグ出力は必ず `stderr` に書く（`>&2`）。データ出力は `stdout`、ログは `stderr` に分離することでリダイレクトやパイプが干渉しない。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forwardエラーの根本原因は「ローカルのHEADがリモートのHEADの祖先でない状態でpushしようとする」こと。自動化スクリプトでは `git pull --rebase origin <branch>` → 変更反映 → `git commit` → `git push` の順序を厳守する。
• rebase中にunstaged changesがあるとrebaseがブロックされる。スクリプト内では `git stash -u` → `git pull --rebase` → `git stash pop` → 変更適用 → `git commit` → `git push` のフローが安全。
• push前に `git status --porcelain` でuncommitted changesの有無を確認し、あればabortするガード節を入れると自動化スクリプトの信頼性が大きく向上する。

**cronとPATH管理**
• cronは `/usr/bin:/bin` など最小限のPATHしか持たず、ユーザーの `.zshrc` や `.bashrc` は一切読み込まれない。crontab冒頭で `SHELL=/bin/bash` と `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin` を明示指定するのが最も確実な回避策。
• コマンドへのフルパス（例: `/usr/local/bin/claude`）を使う方法も有効。デバッグ時は `env > /tmp/cron-env.txt` をcronで実行して実際の環境変数を可視化するとよい。
• `nvm` や `pyenv` などのバージョンマネージャを使う場合、ラッパースクリプト内でバージョンマネージャを初期化してからコマンドを呼び出す必要がある。macOSでは `launchd` の plist に `EnvironmentVariables` を直書きするとPATH問題をより確実に管理できる。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は `if` 文・`||`・`&&` などの条件文脈内ではエラーを**無視する**。`$()` サブシェル内の失敗も親スクリプトに伝播しないため、`result=$(failing_cmd)` は set -e を素通りする。
• `((count++))` は count が 0 のとき終了コード1を返すため、意図せずスクリプトが終了するバグを生む。パイプラインでは `pipefail` なしだと最後のコマンドの終了コードしか取れない（`cat x | grep y` で cat が失敗してもgrepが成功すれば0を返す）。
• 推奨パターン: `set -euo pipefail` の組み合わせに加え、`trap 'echo "Error at line $LINENO, exit $?"' ERR` でエラー箇所をログ出力するとサイレント失敗を防げる。

**git non-fast-forward pushとrebaseの操作順序**
• 自動化スクリプトで `ファイルコピー → commit → pull → push` の順序を誤ると、pullがunstaged changesでブロックされ、その後のpushがnon-fast-forwardになる。正しい順序は `git pull --rebase → ファイル操作 → git add → git commit → git push`。
• `git stash -u` を pull の前に実行してunstaged changesを退避し、pull後に `git stash pop` で戻すパターンも自動化スクリプトで有効。共有ブランチへの force push は禁止し、代わりに `--force-with-lease` を使うとリモートが想定外の状態のとき安全に失敗する。
• `git pull --rebase` はマージコミットを作らず履歴をlinearに保つためCI/CDやbotによる自動コミットと相性が良い。

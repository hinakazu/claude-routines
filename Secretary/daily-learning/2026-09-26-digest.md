**cronとPATH管理**
• cronジョブはシェルの `.zshrc` や `.bashrc` を読み込まないため、ユーザーが設定した PATH は完全に無視される。`crontab` の先頭で `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin` と明示的に指定するか、スクリプト内でフルパスを使うのが基本パターン。
• macOSでは Apple が cron を非推奨とし `launchd` を推奨。launchd の plist でもデフォルトPATHは `/usr/bin:/bin:/usr/sbin:/sbin` のみで狭いため、`EnvironmentVariables` キーで明示指定が必要。
• デバッグは `env > /tmp/cron-env.txt` をジョブ先頭に置いて実際のcron環境を確認するのが定番手順。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` 単体では、条件式（`if`/`||`/`&&`）内のコマンド失敗やサブシェル内のエラーはトリガーされない。`set -euo pipefail` と組み合わせることで、未定義変数参照とパイプライン途中の失敗も捕捉できる。
• `trap 'echo "Error at line $LINENO. Command: $BASH_COMMAND" >> /var/log/script.log' ERR` を追加すると、どの行で何のコマンドが失敗したかをログに残せる。関数・サブシェルへの継承には `-E` フラグが必要。
• grep が「マッチなし（exit 1）」を返す場合など、正常な非ゼロ終了には `|| true` や `|| :` を付けて `set -e` を回避する。

**git non-fast-forward と自動化スクリプトの操作順序**
• 複数箇所からpushが走る自動化リポジトリでは「コミット→pull→push」ではなく「pull→変更→コミット→push」の順序が正解。コミット前にpullすると unstaged changes を rebase がブロックするバグを防げる。
• `git pull --rebase` は履歴をリニアに保つが、共有ブランチへ既にpushしたコミットの rebase は禁忌。自動化スクリプトには `--force-with-lease`（upstream変更を検知して強制pushを防ぐ）を使い、`--force` は使わない。
• pre-commit / pre-push フックでlint・テストを自動実行し、非ゼロ終了でコミットをブロックする構成がCI連携の標準パターン。

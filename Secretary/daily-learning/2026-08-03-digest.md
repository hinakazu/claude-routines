**cronとPATH管理**
• cronはユーザーの `.zshrc` / `.bash_profile` を読み込まず、最小限の `PATH=/usr/bin:/bin` のみで動作する。HomebrewやNode.js等のツールを使う場合は `/opt/homebrew/bin` を含む完全なPATHをスクリプト冒頭に `export PATH=/usr/local/bin:/usr/bin:/bin:/opt/homebrew/bin` と明示指定する必要がある。
• macOSでは `cron` の代わりに `launchd` を使うとより堅牢。plistファイルの `EnvironmentVariables` キーで環境変数を宣言的に管理でき、Macのスリープ中もジョブが蓄積・実行される。
• デバッグの鉄則：cronで動かないコマンドは `env -i /bin/bash --noprofile --norc script.sh` で「cron相当の環境」を再現してローカルテストできる。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は `if` 条件節・`||`/`&&` チェーン中間・パイプラインの非最終コマンドでは**発動しない**。`call && true` は失敗しないが `true && call` は失敗するなど挙動が非直感的。
• ベストプラクティスは `set -eEuo pipefail` ＋ `trap 'echo "ERROR: line $LINENO, exit $?" >&2' ERR` の組み合わせ。`-E`（errtrace）によりERRトラップが関数・サブシェルにも継承されサイレント終了を防げる。
• コマンド置換（`$(...)` 内）では `errexit` が継承されないため、Bash 4.4+ の `inherit_errexit` オプションも追加するか、置換の結果を変数に受けてから明示的にチェックする設計が必要。

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトでgit操作するときの正しい順序は `git pull (--rebase)` → ファイル配置・変更 → `git add` → `git commit` → `git push`。pullを後回しにすると unstaged changes で rebase がブロックされる。
• `git pull --rebase` を使うと余分なマージコミットが生まれず履歴が線形に保たれる。複数の自動化スクリプトが同一リポジトリにpushする構成では特に重要。
• pushが non-fast-forward で失敗した場合のリカバリ：`git fetch origin` → `git rebase origin/main` → `git push` の順で対応。force-pushは共有ブランチでは禁止。

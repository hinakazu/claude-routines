**cronとPATH管理**
• cronジョブはユーザーの `.zshrc` や `.bash_profile` を読み込まないため、PATHは最小限の `/usr/bin:/bin` 程度しかなく、`claude` や `brew` 製コマンドはexit 127で無音終了する。対策の優先順位は①cronファイル冒頭で `PATH=` を絶対パスで明示 → ②スクリプト内でコマンドを絶対パスで呼ぶ → ③ラッパースクリプトで環境をセットアップしてから本体を呼ぶ、の順。
• macOSでは `cron` はすでに非推奨。`launchd` はスリープ復帰後のジョブ再実行、ログ統合、イベントトリガー（ファイル変化など）に対応しており、ラップトップ環境では `launchd` が現在のベストプラクティス。`EnvironmentVariables` キーでPATHを直書きし、`~` は展開されないので `/Users/yourname/` を使うこと。
• `PATH=$PATH:/custom/bin` という書き方はcronの実装によっては変数展開されず文字列リテラルになるため、フルパスを手書きするのが安全。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は `if`/`&&`/`||` の中や `$(...)` サブシェル内では無効化されるため「絶対に終了する保証」はない。`(( i++ ))` のように結果が0の算術式でも即終了するなど、直感に反する動作が多い。「安全そうに見えて実はデバッグを難しくする」のが最大の罠。
• 確実なエラーキャプチャには `trap 'echo "Error at line $LINENO: $BASH_COMMAND (exit $?)" >> /tmp/err.log' ERR` を使う。さらに `set -E`（大文字E）を加えると関数内・サブシェル内にもERRトラップが継承される。`trap cleanup EXIT` を組み合わせてtempファイル削除も漏れなく行う。
• 特定コマンドだけエラーを無視したい場合は `some_cmd || true` が定番。`set -x` をデバッグ時に追加すると各コマンド実行前に展開後の内容が表示されてサイレント失敗の原因特定が速くなる。

**git non-fast-forward push と rebase の操作順序**
• non-fast-forward pushエラーは「リモートにローカルが知らないコミットがある」状態で起きる。自動化スクリプトでは複数のジョブが同一ブランチにpushするケースで頻発する。修正パターンは `git pull --rebase origin <branch> && git push`。mergeではなくrebaseを使うことで余分なマージコミットが生まれず履歴がきれいになる。
• 自動化スクリプトの安全な操作順序：① `git fetch` でリモート状態確認 → ② ファイル操作（cp等） → ③ `git add && git commit` → ④ `git pull --rebase` → ⑤ `git push`。ファイル操作の前にpullをしないとstaged/unstagedな変更があってrebaseがブロックされる。
• conflictが起きた場合を考慮して `git pull --rebase || (git rebase --abort && exit 1)` のようにabortとエラー終了を明示しておくと、スクリプトが中途半端な状態で止まらない。`git fetch --all --prune` を定期的に挟むとローカルの古いリモート追跡ブランチが掃除されて混乱を防げる。

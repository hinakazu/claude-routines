**cronとPATH管理**
• cronはユーザーの`.zshrc`を読み込まず、`/opt/homebrew/bin`や独自インストール先が未登録のままになる。スクリプト冒頭で`PATH=/usr/local/bin:/opt/homebrew/bin:$PATH`を明示するか、コマンドにフルパスを使うのが最も確実な防衛策。
• macOSでは`cron`は公式に非推奨。`launchd`が正式な後継で、スリープ/ウェイク後のジョブ実行漏れがなく、`EnvironmentVariables`にPATHを宣言できるため自動化スクリプトの安定性が段違い。
• launchd の plist では`~`は展開されないため、WorkingDirectoryや標準出力ログのパスは`/Users/yourname/`で絶対指定が必須。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は`||`/`&&`の右辺や`if`の条件式、`local var=$(cmd)`の中ではエラーが無視される。特に`local out=$(some_command)`は`local`コマンド自体が成功扱いになるため、失敗してもスクリプトが止まらない。
• `trap 'handler $LINENO "$BASH_COMMAND" $?' ERR`は`set -e`が無視するケースを捕捉できる。ただしデフォルトでは関数やサブシェルにトラップが継承されないため、`set -E`を併用して継承を有効化するのが必須。
• コマンド置換`$(...)`内での`-e`継承は`shopt -s inherit_errexit`で有効化できる。2026年時点でも`set -eEo pipefail` + `shopt -s inherit_errexit` + `trap ERR`の三点セットが信頼性の高いベストプラクティス。

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトでの正しいgit操作順序は「fetch → pull（rebase）→ 変更適用 → commit → push」。変更ファイルをコピーしてからpullすると、unstaged changesでrebaseがブロックされnon-fast-forwardエラーになる。
• `git config --global pull.rebase true`と`git config --global rerere.enabled true`をセットで設定しておくと、定型的なコンフリクトが自動解消されpull時の手作業を大幅に削減できる。
• CI/CDパイプラインでは pre-pushフックで`git fetch --dry-run`を実行し、ローカルとリモートのdiverseを事前検出してからpushする設計が堅牢。

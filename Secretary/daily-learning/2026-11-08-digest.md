**cronとPATH管理**
• cronはログインプロファイル（.zshrc / .bashrc）を読み込まないため、デフォルトのPATHは `/usr/bin:/bin` のみ。`/Applications/cmux.app/Contents/Resources/bin` などユーザー追加パスは存在しない状態でジョブが実行される。
• 解決策は3段階：①crontabの先頭で `PATH=/usr/local/bin:/usr/bin:/bin:/your/custom/path` を明示する②スクリプト内で絶対パスを使う③`.env`ファイルを `source` するラッパーを作る。crontab内では `PATH=$HOME/bin:$PATH` のような変数展開が動作しないため、リテラルで書く必要がある。
• デバッグ時は `env -i PATH=/usr/bin:/bin HOME=$HOME /bin/bash /path/to/script.sh` でcronと同等の環境を手元で再現できる。ログ出力を `>> /tmp/cron.log 2>&1` で残す習慣も重要。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` には3つの重大な例外がある：①`if`条件式の中のコマンド②`!` で否定されたコマンド③`&&`/`||` チェーンの非最終コマンド。これらは失敗してもスクリプトが終了しない。さらに `$(...)` サブシェル内でも `set -e` は継承されない（Bash 4.4以降なら `set -o inherit_errexit` で解決可能）。
• `((count--))` のような算術式は結果が0になるとexit code 1を返すためスクリプトが終了する。回避策は `((count--)) || true` と書くか、`[[ $count -gt 0 ]] && ((count--))` とする。
• 推奨パターン：クリーンアップには `trap 'rm -f /tmp/work.lock' EXIT`、エラー診断には `trap 'echo "Error at line $LINENO: $BASH_COMMAND" >> /var/log/myscript.log' ERR` を組み合わせる。BashFAQは「set -eを使わず自前でエラーチェックを書く」ことを推奨しているが、trapと組み合わせた上で使う派も多い。

**git non-fast-forward push と rebase の操作順序**
• gitを使った自動化スクリプトの安全な操作順序は `git status --porcelain` で未コミット変更を確認 → 変更があれば中断（またはstash） → `git fetch` → `git rebase origin/main` → `git push --force-with-lease` の5ステップ。pull前にcommitしていない変更があると rebase.autostash が自動stashを適用し、後のreset時にその変更が消える危険がある。
• `git push --force` ではなく `git push --force-with-lease` を使う。これはリモートの期待するSHAと一致している場合のみpushを通すため、他者の変更を誤って上書きするリスクを防ぐ。さらに安全にするには `--force-with-lease=<branch>:<expected-sha>` と明示する。
• pre-rebaseフックに `git diff-index --quiet HEAD -- || { echo 'uncommitted changes exist, aborting'; exit 1; }` を書いておくことで、未コミット変更がある状態でのリベースを自動的にブロックできる（gixリポジトリのサンプルフックより）。

**cronとPATH管理**
• cronジョブはユーザーの `.zshrc` / `.bash_profile` を読み込まず、デフォルトのPATHは `/usr/bin:/bin` のみ。Homebrew（`/opt/homebrew/bin`）や独自ツールは必ず未登録になる。crontab冒頭で `PATH=/usr/local/bin:/opt/homebrew/bin:/usr/bin:/bin` のように完全絶対パスを明示するのが最もシンプルかつ確実な対策。
• `PATH=$PATH:/custom/bin` のような変数展開は cron実装によっては「$PATH」がリテラル文字列になるため禁止。絶対パスのみを列挙する。
• macOSではlaunchdが推奨。cron（`/usr/sbin/cron`）はSleepしているMacでジョブが飛ぶが、launchdはスリープ後の復帰時に missed run を検出して再実行する。SIP（System Integrity Protection）との相性もlaunchdの方が良く、イベント駆動（ファイル変更など）にも対応する。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は `if`文の条件節・`||`/`&&` チェーン・サブシェル内では**エラーで終了しない**。例: `if grep "pattern" file; then` の grep が失敗してもスクリプトは続行される。
• 推奨セットは `set -euo pipefail`。`-u` は未定義変数を空文字展開せずエラーに、`-o pipefail` はパイプライン中間コマンドの失敗を検知する。
• `trap 'echo "Error on line $LINENO: $BASH_COMMAND" >&2' ERR` を組み合わせると、`set -e` が検知しない条件内エラーも `set -E`（errtrace）付きで関数・サブシェルまでトラップ可能になる。自動化スクリプトではログファイルへのリダイレクト（`>> /var/log/myjob.log 2>&1`）と合わせて使うと原因追跡が格段に楽になる。

**git non-fast-forward pushとrebaseの操作順序**
• 自動化スクリプト（CI/CD含む）で複数箇所から同一ブランチにpushする場合、`cp → commit → push` の順でリモートの新コミットを拾い忘れると non-fast-forward エラーが発生する。正しい順序は **`fetch/pull → 変更作業 → commit → push`**。
• `git pull --rebase` は merge commit を作らず線形履歴を保つ点で自動化スクリプト向き。ただし unstaged changes があると rebase がブロックされるため、変更を加える前に `git stash` するかクリーンな状態を保証する。
• MergifyなどのCIツールを使えば「PRマージ前に自動rebase」をルール化でき、開発者が手動でrebaseを意識しなくて済む設計も可能。2026年時点では Gitea にも `ff_only` パラメータが追加され、non-fast-forward mergeをCIレベルで弾けるようになっている。

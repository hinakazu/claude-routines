**cronとPATH管理**
• cronのデフォルトPATHは `/usr/bin:/bin` 程度の最小限のみ。ターミナルで動くコマンドがcronで動かない原因の大半はこれ。解決策は①crontabのヘッダー行に `PATH=...` を明示、②スクリプト冒頭で上書き、③全コマンドを絶対パスで記述の3択。
• macOS（Sequoia以降）ではcronデーモンが事実上機能しないとの報告あり。GUIや Keychain アクセスが必要な処理は launchd の `EnvironmentVariables` キーでPATHを渡すほうが確実。
• cron動作確認は `env -i HOME=$HOME sh -c 'your_script.sh'` でcron環境を再現してからテストするとデバッグが速い。macOSのcronログは `log show --predicate 'process == "cron"' --last 1h` で確認。

**`set -e` のサイレント終了とエラーハンドリング設計**
• 本番スクリプトのヘッダーは `set -euo pipefail` が現代的な標準。`-u` は未定義変数でエラー、`pipefail` はパイプライン途中の失敗を検出する。
• `set -e` が**効かない**4大ケース：①`if`の条件式、② `!` 否定コマンド、③ `||` の前のコマンド、④コマンド置換 `$(...)`。特に `local var=$(失敗コマンド)` は終了コードを捨てる典型的な罠。
• `trap 'echo "Error: line $LINENO, cmd: $BASH_COMMAND" >&2' ERR` でデバッグ情報を残し、`trap cleanup EXIT` でリソース解放。`set -E`（errtrace）を加えないとERRトラップが関数内で継承されない点に注意。

**git non-fast-forward pushと操作順序**
• 自動化スクリプトでのgit操作の正しい順序：`git pull --ff-only` → ファイル更新 → `git add` → `git diff --staged`で確認 → `git commit` → `git push`。pull前にファイルを変更してしまうと `unstaged changes` でrebaseがブロックされる。
• `git pull --ff-only` を使う理由：意図しないマージコミットを防ぐ。fast-forwardできない場合は明示的にエラーで停止するため、スクリプトの制御フローが追いやすい。
• pushが non-fast-forward で失敗した場合はもう一度 pull → push のリトライループを組む。`git config pull.rebase false/true/ff-only` で挙動を固定するか、スクリプト内で毎回フラグを明示するほうが環境依存を避けられる。

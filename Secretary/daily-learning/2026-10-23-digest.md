**cronとPATH管理**
• cronジョブは最小限の環境変数しか引き継がず、ユーザーの`.zshrc`/`.bashrc`はロードされない。スクリプト冒頭で`PATH=/usr/local/bin:/usr/bin:/bin:/path/to/app/bin`のように絶対パスを明示指定するのが最も確実な対策。
• cronファイル冒頭に`PATH=...`を記述する方法もあるが、そのファイル内の全ジョブに適用される。デバッグは`env > /tmp/cron-env.txt`を一時追加して手動実行時と比較する方法が有効。
• macOS Sequoia以降ではcronが実質動作しないケースが増加。launchdのplistで`EnvironmentVariables`キーにPATHを明示設定する方式が推奨されており、sleep中に実行を逃してもシステム起動後に実行される利点もある。

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e`はif文条件式・論理演算子・コマンド置換`$(...)`の内部では適用されないという仕様上の例外が多く、「安全に見えてデバッグを難しくする諸刃の剣」とされる。
• `local result=$(command)` という書き方は`local`自体がexit 0を返すため`command`が失敗してもset -eが発動しない。`local result; result=$(command)` と分けて書くことで回避できる（自動化スクリプトで頻出のバグ）。
• 推奨パターン：`set -euo pipefail` + `trap 'echo "ERR on line $LINENO (exit $?)" >&2' ERR` の組み合わせ。トレースは全体でなく疑わしい箇所だけ`set -x`/`set +x`で囲むと可読性を保てる。

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトで`git pull`をそのまま使うとローカルのpull.rebase設定に依存して挙動が変わる。`git pull --ff-only` または `git pull --rebase` を明示することが安全。
• `--ff-only`はdivergentな状態で失敗して止まるため自動化スクリプトに最も安全。diverge時は明示的なエラーメッセージを出して中断する設計が推奨。
• dirty working tree（未コミットの変更あり）での`git pull --rebase`は失敗する。`git stash -u && git pull --rebase && git stash pop`のパターン、またはgit設定の`rebase.autoStash=true`が有効。
• 安全な自動化の操作順序：`git fetch origin` → `git status`で競合確認 → `git rebase origin/main` → 変更追加 → `git add` → `git commit` → `git push`

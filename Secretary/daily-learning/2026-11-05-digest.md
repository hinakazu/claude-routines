**cronとPATH管理**
• cronはユーザーの`.zshrc`や`.bash_profile`を読み込まないため最小限のPATHのみで実行される。スクリプト冒頭に `PATH=/usr/local/bin:/usr/bin:/bin:$PATH` を明示するか、cronの設定に直接記述するのが確実
• macOSではlaunchdがcronより推奨。`.plist`の`EnvironmentVariables`でPATHを明示でき、Apple Siliconは`/opt/homebrew/bin`を必ず含める必要がある
• launchdのもう一つの優位点：Sleep中にスキップされたジョブを起動後に自動実行する（cronはスキップしたまま）。ラップトップ環境での自動化に特に重要
• `SHELL=/bin/bash` をcrontabに記述しないと `sh` で実行され、bash固有の配列や `[[ ]]` が無音で失敗する

**`set -e` のサイレント終了とエラーハンドリング設計**
• `set -e` は `if` 文の条件やパイプライン内ではエラーを検知しない。`$(cat file)` などのコマンド置換内のエラーもスルーされる
• `((count--))` は結果が0になると終了コード1を返し、スクリプトが意図せず終了する罠がある（`((count--)) || true` で回避）
• 推奨の安全な組み合わせ：`set -euo pipefail` + `trap 'error_handler ${LINENO} $? "$BASH_COMMAND"' ERR` でエラー発生行と終了コードを記録
• 本番スクリプトでは `set -e` に過信せず、重要なコマンドの直後に `|| { echo "failed: xxx" >&2; exit 1; }` を明示的に書くのが堅牢

**git non-fast-forward push と rebase の操作順序**
• 自動化スクリプトの正しい操作順序：`git pull --rebase` → ファイルコピー/生成 → `git add` → `git commit` → `git push`。コピー前にpullを済ませることで"unstaged changes during rebase"を防ぐ
• `git pull --rebase --autostash` を使うと、未ステージの変更があっても自動でstash/unstashしてrebaseを実行できる。CI/CDパイプラインでの衝突防止に有効
• `git config --global pull.rebase true` を設定しておくと常にrebase戦略になり、マージコミットの混入を防ぐ
• `git rerere`（Reuse Recorded Resolution）を有効にすると、同じコンフリクトに対する解決策を記録して再利用できる
